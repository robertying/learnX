# .maestro

- `.maestro/` holds [Maestro](https://docs.maestro.dev) flows driven by the mock login: log in and visit every tab, open a notice / assignment / file, favorite and archive, search, settings pages and logout. `.maestro/subflows/` is only reached through `runFlow`.
- Install the CLI with `brew install mobile-dev-inc/tap/maestro`; it runs on the JDK in `JAVA_HOME` (17+). Build and install a debug app, start Metro, and boot exactly one simulator or emulator (or set `MAESTRO_DEVICE=<udid or serial>`).
- CI (Android only): run Native (`.github/workflows/build.yml`) by hand with "Android E2E tests" ticked. That job installs the APK from "Android release build" (`-PciRelease`: R8 and the bundled JS, signed with the debug key, no Crashlytics uploads, mock login from a generated `.env`) in an API 36 emulator, runs every flow, and uploads Maestro's results with logcat. iOS E2E isn't in CI.
- `pnpm e2e:ios` / `pnpm e2e:android` run every flow; append a path to run one, e.g. `pnpm e2e:android .maestro/03_favorite_archive.yaml`. `scripts/e2e.sh` passes `APP_ID` (the bundle ids differ in case: `io.robertying.learnX` vs `io.robertying.learnx`), the two mock values from `.env` and `ORIENTATION` (`E2E_ORIENTATION`, `PORTRAIT` by default; the login subflow sets it) with `-e`; never hard-code them in a flow.
- `pnpm e2e:devices [profile ...]` (`scripts/e2e-devices.sh`) runs the flows on each device setup in turn, one device at a time: `iphone`, `ipad`, `ipad-landscape`, `duo-folded`, `duo-half`, `duo-open`, `fold-folded` and `fold-unfolded` (all of them by default). It boots a device that isn't running (refusing while `E2E_MAX_BOOTED`, 3, are), shuts down only what it booted, and writes Maestro's output and a JUnit report per profile to `build/e2e/<profile>/`. Install a debug build on each device and start Metro first. The devices are named by `E2E_IPHONE`, `E2E_IPAD`, `E2E_DUO` (simulator names or UDIDs) and `E2E_AVD`; the script's header lists the defaults.
- Each flow starts from `clearState` and logs in with the mock account, so flows are independent and can run in any order.
- Select by `testID` (`id:`) first; otherwise match the visible text or accessibility label as a regex covering both languages (`'Search|搜索'`), so the flows pass in English and Chinese. Regexes must match the whole label, and iOS merges a card's texts into one label (`'课程, 标题, …'`), so match content as `'.*标题.*'`.
- iOS quirks: after a `clearState` launch the native tab bar buttons lose their identifiers in Maestro's snapshot, so tabs are matched as `'tab-files|doc(ument)?\.fill'` (testID or SF Symbol); the login subflow dismisses the "Save Password?" sheet; `hideKeyboard` is flaky, so tap something inert instead. iOS header buttons are native bar items and only expose their label. Text input is ASCII only: Maestro can't type CJK on Android, so search for ASCII mock content.
- Swipe actions are iOS only; Android opens the same actions from a long-press menu (`subflows/card_actions.yaml` handles both). iOS has no system back, so `subflows/back.yaml` swipes from the left edge, and skips it when the list is still on screen (iPad split view).
- The flows are kept passing on every profile of `scripts/e2e-devices.sh`.
- Mac: Maestro supports Android, iOS and web only, so the Mac app has XCUITest tests instead: `ios/learnXUITests` (the `learnXUITests` scheme, a synchronized folder) follows the same five flows, in Chinese (`-AppleLanguages`), and finds the sidebar by its rows' `tab-*` identifiers. Run them with `pnpm e2e:mac` (`scripts/e2e-mac.sh`, which passes the mock login as `TEST_RUNNER_E2E_*`) with Metro running and no other learnX Mac app open. They take over the pointer and keyboard and log out whatever account the debug Mac app has, so only start them by hand, never from an automated session; they aren't in CI. Keep them in step when a flow changes.
- `scrollUntilVisible` swipes the middle of the screen, which is the detail pane on an unfolded foldable or tablet: on Android, swipe the list itself (`swipe` `from: id:` in a `repeat`), as `05_settings_logout` does with `settings-list`.
- iPad: set the simulator to Settings › Multitasking & Gestures › Full Screen Apps; with Windowed Apps Maestro only sees SpringBoard. The tabs sit in a paged top bar (`subflows/tab.yaml` turns the page) and details open beside the list. Landscape comes from `setOrientation` in the login subflow (`ipad-landscape`).
- Android foldable: `scripts/e2e-devices.sh` folds and unfolds it with `adb emu fold` / `adb emu unfold` (`adb shell cmd device_state state` shows the current one). Unfolded, it has the tablet layout (split views), so it stands in for Android tablets.
- iPhone Duo hinge: `simctl` has no command for it; `scripts/e2e-devices.sh` sets it with [`hinge`](https://github.com/artemnovichkov/hinge) (`brew install artemnovichkov/tap/hinge`, or set `E2E_HINGE`), which sends the hinge event that the Simulator's Device Hub slider sends. The app moves to the other display a few seconds after the hinge does.
- iPhone Duo open (`duo-half`, `duo-open`): Maestro on iOS only drives the outer display (mobile-dev-inc/Maestro#3623). With the app on the inner display, its screenshots are black, the app's frames are offset into the outer display's coordinates, and taps don't reach the app. So these profiles log in while closed, open the hinge, and run `.maestro/postures/` instead: each opens a screen from its `learnx://` link (mock item ids, checked by `src/helpers/__tests__/e2ePostures.test.ts`) and checks only its id. The script then saves the inner display (`xcrun simctl io <udid> screenshot --display=3`, 1 = outer, 3 = inner; it can hang, so it has a timeout) and checks that the app is still running. Add tap steps once Maestro can drive the inner display (its `setFoldPosture`, mobile-dev-inc/Maestro#3621, would also replace `hinge`).

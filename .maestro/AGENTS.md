# .maestro

## Setup and running

- `.maestro/` holds [Maestro](https://docs.maestro.dev) flows driven by the mock login: check that the real login reaches Tsinghua's server, log in and visit every tab, open a notice / assignment / file, favorite and archive, search, settings pages and logout. `.maestro/subflows/` is only reached through `runFlow`.
- Install the CLI with `brew install mobile-dev-inc/tap/maestro`; it runs on the JDK in `JAVA_HOME` (17+). Boot exactly one simulator or emulator (or set `MAESTRO_DEVICE=<udid or serial>`) and install the Release build with `scripts/e2e-build.sh ios <udid>` / `scripts/e2e-build.sh android <serial>`: E2E runs always use Release (bundled JS, R8 on Android), never a debug build with Metro. One iOS build installs on every simulator of the same architecture; rebuild after changing app code.
- `pnpm e2e:ios` / `pnpm e2e:android` run every flow (on iOS then the UI tests, see "XCUITest" below); append a path to run one, e.g. `pnpm e2e:android .maestro/03-favorite-archive.yaml`. `scripts/e2e.sh` passes `APP_ID` (the bundle ids differ in case: `io.robertying.learnX` vs `io.robertying.learnx`), the two mock values from `.env` and `ORIENTATION` (`E2E_ORIENTATION`, `PORTRAIT` by default; the login subflow sets it) with `-e`; never hard-code them in a flow.
- `pnpm e2e:devices [profile ...]` (`scripts/e2e-devices.sh`) runs the flows on each device setup in turn, one device at a time: `iphone`, `ipad`, `ipad-landscape`, `ipad-windowed`, `duo-folded`, `duo-half-open`, `duo-open`, `fold-folded` and `fold-unfolded` (all of them by default). It boots a device that isn't running (refusing while `E2E_MAX_BOOTED`, 3, are), shuts down only what it booted, and writes Maestro's output and a JUnit report per profile to `build/e2e/devices/<run start time>/<profile>/`, keeping the latest `E2E_KEEP_RUNS` (10) runs. The flows run on the Release app: install it with `scripts/e2e-build.sh` first, or set `E2E_BUILD=1` to have the script build and install it on each device it uses (one iOS build serves every simulator). The devices are named by `E2E_IPHONE`, `E2E_IPAD`, `E2E_DUO` (simulator names or UDIDs) and `E2E_AVD`; the script's header lists the defaults.
- CI (Android only): "Android E2E tests" in `.github/workflows/ci.yml` runs after every push to `main`, and on a branch when you run CI by hand (Actions › CI › Run workflow). It installs the APK from the "Android" job (`-PciRelease`: R8 and the bundled JS, signed with the debug key, no Crashlytics uploads, mock login from a generated `.env`) in an API 36 emulator, runs every flow, and uploads Maestro's results with logcat. iOS E2E isn't in CI.
- Login check (`00-login-check.yaml`, first in every run, live runs included): the mock account never touches the network, so this flow logs in through the real SSO login with an account that doesn't exist (a username, password and fingerprint made up in the flow, passed as the test login's launch arguments) and waits for the server's wrong-password answer, `bad credential`, at the start of the failure toast. It catches a release build whose login can't reach or read id.tsinghua.edu.cn (a Babel, Metro, Expo or polyfill change that only shows without Metro), which the mock flows can't. Every E2E build is built with `TEST_LOGIN=1` (`scripts/e2e-build.sh`, CI's Android job), which lets it take test logins from launch arguments and makes the toast start with the reason; store builds have neither. It needs id.tsinghua.edu.cn to be reachable from the device.
- Live account (local only, never CI): `pnpm e2e:ios --live` / `pnpm e2e:android --live` run the flows tagged `live` (tabs, details, settings and logout) logged in with `LIVE_USERNAME` / `LIVE_PASSWORD` from `.env`. The build from `scripts/e2e-build.sh` holds no `.env` value for it, only a flag (`TEST_LOGIN`, `babel/inline-env.js`) that lets it take a test login from launch arguments. The login subflow passes `liveUsername` and `liveFingerprint` (`services/launchOptions.ts`; Android forwards them from the launch intent in `MainActivity`), and typing that username signs in with the fingerprint instead of opening the SSO page, which would add a device each run. Store builds ignore those arguments, and the fastlane lanes refuse to run with `TEST_LOGIN` set. Flows get `ACCOUNT` (`mock` or `live`): checks of mock content run only when it's `mock`, and live runs open the first `notice-card` / `assignment-card` / `file-card` (`CARD_ID` in `subflows/open.yaml`), so the account needs one of each this semester. Leave flows that change data (favorite, archive) or depend on mock content (search) untagged. The script keeps Maestro's output, which has the password and fingerprint in it, in a temporary folder it deletes, and clears the app's data afterwards.

## Writing flows

- The flows share one login: `00-reset.yaml` clears the app first (`subflows/reset.yaml`; `executionOrder` in `config.yaml` runs the flows in order and logs out last), and `subflows/login.yaml` relaunches the app with the `mockLatency: none` launch argument (no emulated server delay) and logs in only when the app shows the welcome or login page. A flow run alone starts from whatever the app shows, logged in or not. A flow that changes data (favorites, archives, filters) puts it back before it ends; a flow added outside `flowsOrder` runs after the logout and logs in again. `00-reset` is tagged `live` too, so live runs start fresh. The store flows reset first themselves (`store/subflows/start.yaml`); `STATE_CLEARED` skips the reset for a caller that cleared the app itself.
- Select by `testID` (`id:`) first; otherwise match the visible text or accessibility label in both languages, so the flows pass in English and Chinese. Never copy a label or mock text into a flow: `scripts/e2e-env.mjs` reads them from the translations and the mock data (which follows the app's language, `data/mockEnglish.ts`) and `scripts/e2e.sh` passes them with `-e`: `${T_<key>}` is translation `<key>` as `English|中文` (any key a flow names is passed), and `${MOCK_*}` are the mock items the flows open, listed in that script. Labels the app doesn't own (UIKit's page buttons, the Save Password sheet) are the only text written in flows. Regexes must match the whole label: iOS merges a card's texts into one label (`'Course, Title, …'`) and reads a header button's badge or a menu item's count after its label (`'Settings, New'`), so match content as `'.*(${MOCK_NOTICE}).*'` and such labels as `'(${T_settings})(, .*)?'`. `scripts/__tests__/e2eEnv.test.ts` runs the script and checks that every value a flow uses has both languages; `scripts/__tests__/maestro.test.ts` checks that every flow in `config.yaml`'s `flowsOrder` exists by its `name:` and that every `runFlow` / `runScript` file does.
- Keep runs fast: a `when: visible` on an element that isn't there (or a `notVisible` on one that is), an `optional` tap that finds nothing and an `optional` `extendedWaitUntil` each wait out Maestro's lookup timeout (7 s, or the given timeout). Branch on what's known instead: `platform`, `true: ${IPAD == 'true'}` (`scripts/e2e.sh` sets `IPAD` on an iPad simulator), or `copyTextFrom` on the element that did show, as `subflows/login-form.yaml` does for the "Save Password?" alert some iOS devices show.
- Keep `$` out of `${...}` scripts (a regex's `$` anchor, `/x$/`): Maestro then doesn't evaluate the script, and its raw text counts as true in a `when: true:`. Compare strings instead, as `subflows/login-form.yaml` does.
- Card actions are tapped in the long-press menu (the context menu on iOS, the Material menu on Android; `subflows/card-actions.yaml`) by their translated text, since the iOS menu's items have no ids. iOS has no system back, so `subflows/back.yaml` swipes from the left edge, and skips it when the list is still on screen (iPad split view).
- The flows are kept passing on every profile of `scripts/e2e-devices.sh`, in both languages (switch the simulator with `simctl spawn <udid> defaults write -g AppleLanguages '("zh-Hans")'` and a reboot, the emulator app with `cmd locale set-app-locales`), and in the manual Android CI job.

## Platform quirks

- iOS quirks: after a `clearState` launch the native tab bar buttons lose their identifiers in Maestro's snapshot, so tabs are matched as `'tab-files|folder\.fill'` (testID or the filled SF Symbol from `filledSymbols` in `navigation/MainTab.tsx`; Today's follows the time of day, so its regex lists all four); the login subflow dismisses the "Save Password?" sheet; `hideKeyboard` is flaky, so tap something inert instead. iOS header buttons are native bar items and only expose their label. Text input is ASCII only: Maestro can't type CJK on Android, so search for ASCII mock content.
- Released Maestro's iOS driver loses screens whose accessibility tree is 60 or more levels deep (the notice detail is 66) unless a leftover keyboard window exists, which only a login in the same launch leaves behind: it then sees only the status bar. The patched Maestro fixes this (`scripts/maestro/maestro-hierarchy-fallback.patch`, built by `scripts/maestro/build.sh`). So that released Maestro passes too, `02-details` runs right after the reset and logs in itself.
- Bring a list row on screen before tapping it with `subflows/scroll-list.yaml`, which swipes the list itself by its testID, on both platforms. `scrollUntilVisible` swipes the middle of the screen, which is the detail pane in a split view (iPad, unfolded foldable). A row counts as visible under the floating tab bar or, on iOS, under the navigation bar, where a tap lands on the bar: scroll a row near the end of a list to the end, and one near the top back to the top, with one swipe more than it takes to show it (`05-settings-logout`).
- iPad: set the simulator to Settings › Multitasking & Gestures › Full Screen Apps; with Windowed Apps Maestro only sees SpringBoard. The tabs sit in a top bar that pages when its labels don't fit (English portrait; `subflows/tab.yaml` turns the page for Today and Courses, the only tabs that can be off the current page) and details open beside the list. Landscape comes from `setOrientation` in the login subflow (`ipad-landscape`). `ipad-windowed` runs every flow on a second iPad simulator set to Windowed Apps (`E2E_IPAD_WINDOWED`), in the app's default window; it needs the patched Maestro (`scripts/maestro/build.sh`), since released Maestro offsets a window that isn't full screen and only sees SpringBoard.
- Android foldable: `scripts/e2e-devices.sh` folds and unfolds it with `adb emu fold` / `adb emu unfold` (`adb shell cmd device_state state` shows the current one). Unfolded, it has the tablet layout (split views), so it stands in for Android tablets.
- iPhone Duo hinge: `simctl` has no command for it; `scripts/e2e-devices.sh` sets it with `subflows/fold.yaml` (`setFoldPosture: closed|halfFold|flat`), which only the patched Maestro has (`scripts/maestro/build.sh`; upstream mobile-dev-inc/Maestro#3621): put its bin folder first on `PATH`. It sends the hinge event that the Simulator's Device Hub slider sends and returns once the simulator reports the angle; the app moves to the other display soon after, so wait for an id of the new layout rather than sleeping.
- iPhone Duo open (`duo-half-open`, `duo-open`): The patched Maestro reads the inner display's elements and screenshots it, but no public tool sends touches to it: simctl, devicectl and XCTest take no display, and Maestro's taps there do nothing. So these profiles log in while closed, open the hinge, and run `.maestro/postures/` instead: each opens a screen from its `learnx://` link (mock item ids, checked by `scripts/__tests__/e2ePostures.test.ts`) and checks only its id. The script then saves the inner display (`xcrun simctl io <udid> screenshot --display=3`, 1 = outer, 3 = inner; while the Duo is open a screenshot needs `--display`, and it can hang, so it has a timeout) and checks that the app is still running.

## XCUITest (Mac and iOS)

- Mac: Maestro supports Android, iOS and web only, so the Mac app has XCUITest tests instead: `ios/learnXUITests/Mac` (the `learnXUITests` scheme, a synchronized folder; `Mac/` compiles for Mac Catalyst only) follows the same five flows, in Chinese (`-AppleLanguages`), and finds the sidebar by its rows' `tab-*` identifiers. Run them with `pnpm e2e:mac` (`scripts/e2e-mac.sh`, which passes the mock login as `TEST_RUNNER_E2E_*` and stops a test after 3 minutes, since XCUITest can hang quitting the app after a failure) on the Release app, with no other learnX Mac app open. They take over the pointer and keyboard and log out whatever account the learnX Mac app has, so only start them by hand, never from an automated session; they aren't in CI. Keep them in step when a flow changes.
- iOS: `ios/learnXUITests/iOS` (compiled out on Mac Catalyst) checks what a flow can't see, each test for the kind of device it needs and skipped on others: the Today spinner's pixels while pull to refresh is held (`TodayUITests`, iPhone), and on an iPad where the split columns' bars sit against the tab bar, the sidebar choice across a relaunch and, on an iPad mini in portrait (744 points, `maxCollapsedWidth`), a notice opening over the list (`SplitViewUITests`). `pnpm e2e:ios` runs them after the flows on the same simulator (`scripts/e2e.sh ios`: Release, the mock login as `TEST_RUNNER_E2E_*`; `--ui [-only-testing:learnXUITests/<class>]` runs only them, `E2E_UI_TESTS=0` skips them), and `pnpm e2e:devices` on its `iphone` and `ipad` profiles. They use the simulator's own touch and keyboard, so they can run from an automated session. They aren't in CI. The iPad mini test needs a run on one: create a `learnX iPad mini` simulator (`xcrun simctl create "learnX iPad mini" com.apple.CoreSimulator.SimDeviceType.iPad-mini-A17-Pro <runtime>`), run `scripts/e2e.sh ios --ui` on it and delete it afterwards.

## Store screenshots

- `.maestro/store/` takes the App Store and Google Play screenshots with the same subflows: `pnpm e2e:store <iphone|duo-folded|duo-half-open|duo-open|ipad|android-phone|android-tablet> [device]` (`scripts/store-screenshots.sh`, its header lists the settings) sets the device up (iOS status bar, Android screen size, density and app locale), runs the target's flow and saves `NN-<slug>.png` under `STORE_OUT_DIR` (default `build/store-screenshots/`). The test runs leave `store/` out (`config.yaml` only takes the top-level flows). Each shot comes after a wait for its screen's testID or mock text, so a wrong screen fails the run instead of being saved. The shots are in Chinese: iOS launches with `APP_LANGUAGE` (`AppleLanguages`), Android takes the app locale the script sets. `duo-half-open` and `duo-open` run the iPhone flow on the closed Duo and open the hinge only for each shot (`store/subflows/screenshot-posture.yaml`, which the script swaps in for `subflows/screenshot.yaml`), so they need the patched Maestro. `mac` runs `ios/learnXUITests/Mac/StoreScreenshots.swift` through `scripts/e2e-mac.sh` (which otherwise skips it), the same screens as the iPad with context menus for the swipe actions, and saves the window shots from the test's attachments to `macos/windows/` for composing; like the other Mac tests it takes over the pointer, so start it by hand.

## Upgrade test

- `.maestro/upgrade/` isn't in the normal run: `scripts/e2e-upgrade.sh ios <udid>` / `android <serial>` runs it. `1-use-18.0.3.yaml` drives 18.0.3 (English labels, no testIDs), `2-after-upgrade.yaml` runs on the current build installed over it and checks the `storeReport` JSON with `check-report.js`, whose expected values are 18.0.3's mock data. 18.0.3 has no testIDs, so its flow taps switches by position on a phone layout; on Android the script folds a foldable emulator first. The calendar and reminder list 18.0.3 makes outlive the app, and 18.0.3 adds its events to the ones it finds by title, so the flow first deletes an earlier run's with 18.0.3's own Delete Synced Calendars & Reminders.

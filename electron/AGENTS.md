# The Electron app (Windows and Linux)

An Electron app around a React Native Web build of the app's own code, drawn with Fluent UI React v9 so it looks like a Windows app. Its web build and E2E tests are required pull request checks, and it's released with the phones on the same GitHub release, though a mobile release never waits on it. Never macOS: the Mac has the Catalyst app.

## Running it

- `pnpm electron` (`dev.ts`, whose header lists its options) exports the web build and opens it in Electron. The first run downloads Electron itself: `pnpm install` skips Electron's download script (`allowBuilds` in `pnpm-workspace.yaml`), so mobile installs never fetch it.
- On Linux a dev run turns Chromium's sandbox off: the downloaded Electron's `chrome-sandbox` isn't setuid root, and Ubuntu 24.04 and later block the user namespaces the sandbox needs otherwise. Packaged builds keep the sandbox.
- A dev run keeps everything it writes in `build/electron/data`, and the saved login out of the system's key store, so dev runs and the E2E tests work with a locked keyring or none (CI). On a Mac it opens a renamed copy of Electron with the app's icon (`macDevApp.ts`), so the Dock, Activity Monitor and LaunchServices say learnX; with the executable renamed, Electron reports `app.isPackaged` as true, so `main.ts` tells dev runs apart another way. `pnpm electron:clean` removes what dev runs leave on a Mac, and never what belongs to the Mac Catalyst app or to stock Electron.
- A dev run never posts system notifications (on a Mac they'd leave a learnX entry in System Settings) or changes Start at login; it logs them instead. `LEARNX_NOTIFICATIONS=system` and `LEARNX_ALLOW_LOGIN_ITEM=1` turn them on; don't set the second on the Mac you develop on. With `--inspect`, `learnxDev` in the main process reaches the logged notifications and the tray, as the E2E tests do.
- `--capture <dir>` and the DevTools Protocol (`-- --remote-debugging-port=9222`) are the ways to see the window from a script. A window's capture leaves out its web views and the PDF viewer's frame; capture over the protocol to include them. `LEARNX_COLOR_SCHEME` sets the window's appearance, which DevTools' color scheme emulation doesn't reach.

## Main process

- It's TypeScript with no build step: Electron's Node strips the types as it loads the files, as Node does for the dev and packaging scripts. So the code is ES modules, imports name the `.ts` file, and only syntax Node can strip is allowed (`erasableSyntaxOnly`, `verbatimModuleSyntax` in `tsconfig.json`). The preloads are the exception: a sandboxed preload runs without Node's module loader, so they're CommonJS (`.cts`), stripped into `.cjs` files as a dev run starts and when packaging (`preloads.ts`). `preload.cts` is typed by the page's own declaration of the bridge (`src/web/bridgeTypes.ts`), so the two sides can't drift apart.
- The app id is `io.robertying.learnXElectron`: `io.robertying.learnX.<name>` is for the iOS app's extensions, and `io.robertying.learnX` is the Mac Catalyst app's.
- The window serves the web build from `app://learnx/` (`appOrigin.ts`) in a session of its own, the only one that serves `app://`, so a page in a web view can't load the app's scripts or a download's preview. That session is saved to disk because Chromium keeps no code cache for an in-memory one, and the web build is large to compile at each launch.
- On Linux the window shows at once instead of on `ready-to-show`: under Wayland a window that was never shown gets no frames, so a page that first draws after a large script never draws.
- The page runs sandboxed and context-isolated. Every IPC handler checks that the call comes from the window's main frame on `app://learnx/` (`fromApp`), never from a web view or a frame, and a test checks every channel the preload uses. Web views get no permissions beyond what `webviewPermission` allows.
- What the main process and the page share is kept once in `src/constants` and read by both (`shared.ts`).
- `net.ts` runs requests to Tsinghua's sites (and courseX) with the window session's cookies, following redirects itself to record the final URL (Electron's `net.fetch` leaves `Response.url` empty). Only over https: a plain http URL to them, given or redirected to, is sent over https, since their cookies would go out in the clear. Other hosts are refused.
- `webviews.ts` hardens every web view as it attaches, whatever its attributes ask, and holds every top-level load until the page decides, so a form's POST goes ahead as sent; plain http to the allowed sites goes to https first; anything off the allowed sites opens in the browser. HTML loads as a data URL at its base URL, as the phones' `loadHTMLString` does, unless it's past Chromium's 2 MB URL limit (a notice with a pasted picture): then it's served to that one request through the web view's DevTools protocol.
- `files.ts` is learnX's own files, for expo-file-system's stand-in: every path must lie in the app's folders, or in a folder the user just picked for an export, and only for what an export does. Downloads fail on a non-2xx status as expo-file-system's do, so thu-learn-lib's download check and re-login work as on the phone. On Windows a download gets the `Zone.Identifier` stream a browser writes, so Windows and Office warn as they do for a browser's download.
- The app's data folder is moved to the local profile on Windows: Electron's default, `%APPDATA%`, roams to other PCs at every sign-in on domains with roaming profiles, downloads and all. Uninstalling removes it (`installer.nsh`); on Linux it stays, and the privacy policy says so.
- `fileStore.ts` writes key-value storage as one file per key, atomically, retrying while Windows reports the file busy. Keys that differ only in case get different files, for NTFS and APFS. The page doesn't wait for writes, so a failed one is logged, never thrown.
- `secrets.ts` keeps the saved login encrypted with `safeStorage` and refuses to save where the system has no key of its own (on Linux, Chromium's fallback key). It uses only the asynchronous APIs: the synchronous ones ask the keyring on the main process's thread, so a locked GNOME keyring (as an automatic login leaves it) would block the window for as long as its unlock prompt is up.
- `system.ts` is what's around the window. Closing it keeps learnX in the tray on Windows and the Dock on macOS; on Linux it quits, since GNOME shows no tray icons without an extension and nothing tells whether one would show. The tray's labels come from the page, in its language; Windows and Linux menus, dialogs and notifications draw no gap between Chinese and Latin text, so it's typed in (`web/systemText`). On Linux, tray actions bring the window forward first: GNOME's tray extension starts a launch (a busy cursor) that only a window coming forward ends. The background sync runs on a main-process timer, since a hidden window's timers slow down. Start at login is written only when its switch changes, and read with the same arguments it's written with: Windows reports a Run key whose arguments differ as off. The app holds a single instance, so a second launch (the Jump List) hands its arguments to the first.
- `language.ts`: Windows and Linux have no per-app language, so Settings › Language there picks one, applied as Chromium's `--lang` at the next launch, which everything else follows.
- `notifications.ts` posts notifications and reminders while learnX runs. Windows and Linux have no subtitle, so the course goes in the body. There are no action buttons.
- `fileShell.ts` does what reaches outside learnX's folders, always through a dialog the user answers or the system. A file that would run as a program opens only after a confirmation. Downloads are served to the file preview from an origin of their own (`app://files/`), so a downloaded file never reaches the app's page or its bridge, and only PDFs and pictures are served.
- `pdfViewer.ts` gives Chromium's PDF viewer the app's color scheme as its frames load and when the system's appearance changes. The viewer declares none and always reports `prefers-color-scheme: dark`, so Chromium draws its scroll bars light otherwise, whatever the appearance.
- Tests are in `__tests__`, run by Jest's `tooling` project, which loads the main process as Node does (`babel/jest-node-esm.js`) and the preloads as they ship (`jest/stripTypes.js`).

## Packaging and updates

- `pnpm electron:package` (`package.ts`, whose header lists its options; config in `packageConfig.ts`) builds the Windows and Linux installers on a Mac, Windows or Linux. Builds are unsigned. Their Electron fuses turn off running as plain Node, `NODE_OPTIONS` and `file://` privileges; `--inspect` stays, since the packaged E2E tests launch through it. The Windows installer is per user, never in Program Files, so updates install without elevation. The AppImage uses electron-builder's static runtime, which needs neither libfuse2 nor `libz.so` on the host. Ubuntu 24.04 and later block the user namespaces Chromium's sandbox needs and an AppImage can't change that, so its AppRun turns the sandbox off there; the .deb installs an AppArmor profile instead, and the README points Ubuntu users to the .deb. Some electron-builder toolsets are Intel-only on macOS (`makensis` in the legacy NSIS bundle), and a test keeps them out. File names have no spaces, since GitHub turns spaces in asset names into dots and the links in `latest.yml` would break. CI's `Electron / Installers` (by hand) only checks that packaging works; releases are built by hand (the release skill).
- Icons are made from the Icon Composer source by `node electron/icons/generate.ts` on a Mac with Xcode, sized as each platform's own icons are. It makes the README's logo (`docs/assets/logo.webp`, which needs `cwebp`) too. Run it after the icon changes and commit the outputs: Windows and CI can't make them.
- `buildInfo.ts` takes the version and build number from `package.json` and the Xcode project. The committed build number is only what local builds get: a release build passes its own (`pnpm electron:package --build <number>`, which fastlane's build lane does).
- Updates (`updater.ts`, electron-updater) come from the TUNA mirror's copy of the latest GitHub release. An NSIS install or AppImage downloads in the background and installs on quit or Restart. A .deb can't install updates without an administrator's password: it downloads and checks the new .deb the same way (electron-updater's `DebUpdater`), and Settings opens it in the system's installer, which asks for the password (shown in its folder where nothing opens .debs). It checks 10 seconds after launch and every 4 hours, also in the tray, and the page posts a notification once per version, also while the window is in front, but not before logging in (it waits until someone does; the update installs on quit regardless) (`services/updateNotifications.web`; Settings › Notifications › New Versions). electron-updater checks the download's SHA-512 against the update file, and `updateSignature.ts` refuses an update file without a valid detached Ed25519 signature by learnX's Electron update key, whose public half the app carries (`certs/electron-public-key.pem`), and one whose installers are for another platform or CPU (every platform's update file is signed with the same key). So the mirror alone can't make an install run anything, even though the installers are unsigned. Checks carry no id of the install: electron-updater's staging id (for staged rollouts, which releases don't use) is left out. The mirror copies a release on a schedule, so a check can find the new update file before the installer; that download fails and a later check tries again.
- The Electron update key is its own, not the over-the-air one. Its private half is never in the repo. A placeholder key file is refused by the signing script and by packaging (except for builds never to be released), and a test checks that the committed key is a real Ed25519 key. To rotate it, make a new pair in the repo root with Node's crypto (macOS's LibreSSL can't make Ed25519 keys):

  ```bash
  node -e "const c=require('crypto'),fs=require('fs');const k=c.generateKeyPairSync('ed25519');fs.writeFileSync('learnx-electron-private-key.pem',k.privateKey.export({type:'pkcs8',format:'pem'}),{mode:0o600});fs.writeFileSync('certs/electron-public-key.pem',k.publicKey.export({type:'spki',format:'pem'}))"
  ```

  Then store the private key where the old one was kept, delete the file, and commit `certs/electron-public-key.pem`. Installs only trust the key they were built with, so the first release with a new key reaches users only through a download: rotate only if the private half leaks.

- Trying updates without publishing: `node electron/updateServer.ts <dir>` serves a folder as the mirror serves the release. Point a test build or a dev run at it (`--update-url`, `LEARNX_UPDATE_URL`); a dev run can trust a throwaway key (`LEARNX_UPDATE_PUBLIC_KEY`). A Mac dev run gets as far as the download: Squirrel.Mac refuses an unsigned app.
- `pnpm e2e:electron:update` (`updateE2E.ts`) runs a real update on Windows or Linux, as `scripts/e2e/e2e-updater.sh` does for the Android APKs: it packages 99.0.0 and 99.0.1 trusting a throwaway key made for the run, installs 99.0.0 (the NSIS installer, or the AppImage), serves 99.0.1 and has `e2e/installUpdate.e2e.ts` update it from Settings and check that it comes back as 99.0.1. The installer installs where a real learnX would, so it refuses to run where learnX is installed. CI's `Electron / Update E2E tests` runs it on manual runs only, as Android's updater test; the release and upgrade-dependencies skills say when.

## E2E tests (Playwright)

- `pnpm e2e:electron` runs the tests in `e2e/` (`playwright.config.ts` has the workers, timeouts and retries). Append a file or `-g <title>` to run some. They need the web build exported with the mock login in `.env`, and the network: the mock account's files download from GitHub, and the SSO tests skip themselves when id.tsinghua.edu.cn doesn't answer, as from CI's runners abroad at times. CI runs them on Windows and Linux, and the window test again under a headless Wayland compositor.
- E2E runs never come to the front, so you can keep working while they run: windows show behind the others without focus (on a Mac not at all) and render with background throttling off. They also let the system's pointer pass through, since a window opening or closing under it (another worker's) or your mouse would end a hover a test made. A window that was never shown hardly draws on Windows and Linux (no frames under Wayland, about two a second on Windows), which made every test crawl; `window.e2e.ts` checks the window shows and draws at full rate. Tests assert what the app asked for, not what the OS shows.
- `e2e/fixtures.ts` gives each test a fresh data folder and a dev run of the checkout on it, with the launch options the Maestro flows use, and can `relaunch()` it. `LEARNX_E2E_APP=<executable>` tests a packaged app instead; tests that need a dev run's hooks skip themselves there.
- `e2e/mainProcess.ts` stands in, inside the main process, for what Playwright can't click (dialogs, notifications, the shell, Start at login, native menus, the tray, relaunch, install on quit), so nothing reaches the system, and records what the app asked for. The stand-ins patch Electron's modules, so main-process code must call them as `dialog.showOpenDialog(…)`, not through a copy taken at startup.
- `e2e/steps.ts` holds the subflows' counterparts. The window is wide enough for the split views, so a detail, and what a detail opens as a sheet on the phone (the submission page, a course's courseX), opens beside its list, behind a back link (`goBack`). Search and the sheets about the whole app cover the window, as on Android.
- Select as the Maestro flows do: `getByTestId` for `testID`s, roles and text for the rest, with `e2e/maestroEnv.ts`'s `text('MOCK_NOTICE')` and `text('T_<key>')` for the flows' `${…}` values. Tabs and split panes stay mounted when hidden, so match what shows (`steps.ts`'s `shown()`). No fixed waits. The window sends input over a web view by the last frame it drew, not by the DOM Playwright just checked, so after a page covers one (a pushed page over a notice or assignment), wait for `steps.ts`'s `drawn()` before clicking.
- Each spec that ports a Maestro flow names it, and says what differs, in its first comment. Flows for what the Electron app doesn't have (notification actions, over-the-air updates, store screenshots, the APK updater, the 18.0.3 upgrade) have no spec. The other specs cover what only the Electron app does.

## Logging in

- A first login opens Tsinghua's login page in a web view, as `screens/SSO.tsx` does on the phone, and saves the captured form once Web Learning is reached. An expired session is found and handled by thu-learn-lib as on the phone; the main process records the final URL of a redirect so it can.
- Logging out clears everything the web views' session keeps (cookies, site storage and the HTTP cache), not only its cookies, so the next person on a shared computer finds nothing of the last one's.

## The page (`src/web`)

- Web variants use platform extensions. Metro tries every platform for one extension before the next, so a `.web.tsx` file loses to a `.ts` base file: give the base file the variant's extension. The root `AGENTS.md` says where Electron code goes.
- `index.web.js` renders the app inside `web/FluentRoot`. `src/polyfills.web.js` sends the page's requests through the main process, fills in `PlatformColor` as CSS variables that follow the system's appearance, and makes `Alert.alert` a Fluent dialog (React Native Web's does nothing). `FluentRoot` keeps one Tabster (Fluent's focus manager) for the app's lifetime: Fluent disposes of it with the last control that used it, and a dialog that was that control took the page's `aria-hidden` restore with it.
- Each `@expo/ui` pair has a `.web.tsx` variant with Fluent UI, whose props come from the pair's `.shared.ts`. Icons are Fluent System Icons imported one by one in `web/fluentIcons`. Never import icons from `@fluentui/react-icons`' index: it has every icon (tens of MB) and the web build doesn't tree-shake, which is also why Metro resolves Fluent's own imports of it to `web/packages/fluentReactIcons` (regenerate its list when Fluent adds icons; a test checks it). Fluent copies `FluentProvider`'s classes onto its portals, so the root's size is a style.
- The tab navigator's stand-in is Windows' navigation pane, with Settings at its foot. Tabs that aren't selected, like screens under another in a stack, stay mounted as `display: none`; FlashList is patched to measure a list only while it's laid out, since a hidden one measured every row as 0 px tall and rendered them all (`patches/README.md`). Headers title the page at the start and space their buttons as a command bar's. The list column's divider drags (`navigation/SplitDivider.web`); its width and the pane's expanded or collapsed choice are kept per install, like the window's size, not with the account's settings (`navigation/paneLayout`).
- `modules/menus/index.web.tsx` turns the keyboard shortcuts into the menu bar commands the app listens to (and Alt+←, the mouse's back button and Esc into back and close, `navigation/useBackKeys`), and shows a card's actions as a native menu on right-click and as buttons while the pointer is on the card (cards don't swipe here).
- Packages with no usable web build resolve to the stand-ins `src/web/aliases.json` names, on web only, all in `src/web/packages`. They're tested with a fake bridge (`test-utils/mocks/electronBridge`); what renders Fluent UI is tested in Jest's `web` project.
- What `index.js` starts runs as on the phone, with the stand-ins: of the surfaces, only the reminders do anything. Windows and Linux have no calendar on the device to sync to, so Settings › Calendar exports an .ics file instead.

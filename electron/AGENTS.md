# The Electron app (Windows, later Linux)

An experimental, best-effort build: an Electron app around a React Native Web build of the app's own code, drawn with Fluent UI React v9 so it looks like a Windows app. Mobile releases never wait on it and its checks aren't required. Phases 1 to 4 of the plan are done: the app runs, the mock and live logins work (the SSO page for a first login, re-login when the session expires, logout), web pages and notice bodies show, attachments download, it has the Windows UI, and the desktop services: previewing, opening and saving files, picking and dropping files to submit, notifications and reminders, the tray with the background sync, Start at login, the .ics export and the Jump List. Packaging comes in phase 5.

## Running it

- `pnpm electron` exports the web build (`expo export -p web`) to `build/electron/web` and opens it in Electron; `--skip-export` reuses the last export. The first run downloads Electron itself into this package's `node_modules`: `pnpm install` skips Electron's download script (`allowBuilds` in `pnpm-workspace.yaml`), so mobile installs never fetch it.
- In development everything Electron writes stays in `build/electron/data` and `--use-mock-keychain` keeps `safeStorage` out of the macOS keychain. On a Mac the runner opens `build/electron/learnX.app` (`macDevApp.mjs`), a copy of the downloaded `Electron.app` renamed as `@electron/packager` would: `learnX` with the id `io.robertying.learnXElectron`, helpers `learnX Helper` (`(GPU)`, `(Renderer)`, `(Plugin)`) with the id `io.robertying.learnXElectron.helper`, and the Mac Catalyst app's icon compiled by `actool` from `ios/learnX/AppIcon.icon`, signed ad hoc. So the Dock, the menu bar, Activity Monitor and LaunchServices say learnX, and the preferences it writes are `io.robertying.learnXElectron`'s. It's made again when Electron's version or the icon changes (`learnX.app.json` next to it). With the executable renamed, `app.isPackaged` is true (Electron only looks at the executable's name), so `main.cjs` takes a run that opened its folder (`process.defaultApp`) as a dev run too. Windows and Linux run the stock Electron: there, `setAppUserModelId` and the app name do what's possible without packaging.
- `pnpm electron:clean` (`clean.mjs`) removes what dev runs leave on a Mac and prints each item: the dev data folder; the preferences of `io.robertying.learnXElectron` and of `com.github.Electron` (from runs of the stock `Electron.app`); folders under `~/Library` (Application Support, Caches, HTTPStorages, Saved Application State, Logs, WebKit) named after either id or `learnX`; LaunchServices' entries for this checkout's `learnX.app` and `Electron.app` (`lsregister -u`); and keychain items for "learnX Safe Storage" or "Electron Safe Storage". It never touches the Mac Catalyst app's `io.robertying.learnX`, and leaves `learnX.app` for the next run (`build/` goes with the checkout). Run it after testing.
- `--capture <dir>` lets the page save window captures (`await learnx.capture('name')`, `webContents.capturePage` with background throttling off, web views included). A window's capture leaves its web views out, so each is saved next to it as `<name>-webview-<n>.png`. Pass `-- --remote-debugging-port=9222` to drive the window over the Chrome DevTools Protocol (web views are targets of their own there; `Emulation.setDeviceMetricsOverride` tries narrower window sizes) and `--inspect=9229` for the main process. `LEARNX_COLOR_SCHEME=dark` (or `light`) sets the window's appearance whatever the system's (`nativeTheme.themeSource`), which reaches `prefers-color-scheme` and so the app's theme; DevTools' color scheme emulation doesn't.
- A dev run never posts system notifications (on a Mac they'd leave a learnX entry in System Settings › Notifications): it logs each (`[notification] title | subtitle | body`) and the page shows it as a toast. `LEARNX_NOTIFICATIONS=system` posts real ones; check those on Windows. With `--inspect`, `learnxDev.notifications.at(-1).click()` clicks the last one and `learnxDev.tray()` is the tray. A dev run never changes Start at login either (it logs what it would have done) unless `LEARNX_ALLOW_LOGIN_ITEM=1`; don't set that on the Mac you develop on.
- The file preview's PDF viewer is a frame of its own that `learnx.capture` leaves out; capture the window over the DevTools Protocol (`Page.captureScreenshot` on the page's target) to include it.
- `LEARNX_LAUNCH_OPTIONS` (JSON) gives the app a test run's launch options (`src/services/launchOptions`) as its root props, as Android's launch extras do. The live test login (`liveUsername`, `liveFingerprint`) also needs `TEST_LOGIN=1` for the export.

## Main process

- `main.cjs` names the app learnX (`app.setName`, `productName`), with the app id `io.robertying.learnXElectron` (`setAppUserModelId` on Windows), named as a top-level target like `io.robertying.learnXTests`: `io.robertying.learnX.<name>` is for the iOS app's extensions, and the iOS bundle id is the Mac Catalyst app's. It serves the web build from `app://learnx/` with a content security policy, keeps the window on the app (links open in the browser), and registers nothing with the system.
- The page runs sandboxed and context-isolated; `preload.cjs` exposes `window.learnx`, and every IPC handler checks that the call comes from the window's `app://learnx/`, never from a web view.
- `net.cjs`: requests to Tsinghua's sites (and courseX) run here with `net.request` and the window session's cookies, following redirects itself to record the final URL (Electron's `net.fetch` leaves `Response.url` empty). Other hosts, and redirects to them, are refused.
- `webviews.cjs`: the page's web views (`<webview>`, the `react-native-webview` stand-in). Each is hardened as it attaches: the window's session (`persist:learnx`, so it shares the cookies), the sandbox, context isolation and learnX's own preload (`webviewPreload.cjs`, which gives the page `window.ReactNativeWebView.postMessage` and runs the injected scripts), whatever its attributes ask; a page may only turn JavaScript off. Every top-level load waits in `webRequest.onBeforeRequest` while the page decides (`onShouldStartLoadWithRequest`, `originWhitelist`), so a form's POST goes ahead as sent; a load the page allows off Tsinghua's sites, courseX and learnX's GitHub pages opens in the browser instead, as do new windows and mail links.
- `files.cjs`: learnX's own files, under `Files/Caches` and `Files/Documents` in the app's data folder, for expo-file-system's stand-in; every path must lie in them. Downloads run here with the session's cookies, from Tsinghua's sites and courseX (and the mock account's files on GitHub), and fail on a status other than 2xx as expo-file-system's do, so thu-learn-lib's download check and re-login work as on the phone.
- `fileStore.cjs`: key-value storage as one file per key under the app's data folder, written through a temporary file. `secrets.cjs` keeps the saved login in it encrypted with `safeStorage`, and refuses to save where the system has no encryption.
- `electron-builder.config.cjs` is the packaging config (NSIS for Windows, AppImage for Linux, unsigned); electron-builder itself isn't installed until packaging (phase 5).
- `desktop.cjs` is what's around the window, set up by `main.cjs`. Closing the window hides it (learnX stays in the tray on Windows and Linux, and in the Dock on macOS, where Quit ends it), and the tray's menu has Open learnX, Refresh (a background sync now) and Quit, labeled in the page's language (`desktop:setLabels`). The background sync runs on a timer here, every 15 minutes as the page registers it (`web/packages/backgroundTask`), and after the computer wakes, so a hidden window's slowed timers don't hold it back; the page runs `services/background`. Start at login (`app.setLoginItemSettings`, Windows and macOS; on Windows with `--hidden`, which starts in the tray) is read for Settings and written only when its switch changes. On Windows the Jump List (`app.setUserTasks`) has Today and Schedule, which launch learnX with `--learnx-open=<screen>`: the app holds a single instance, so a second launch hands its arguments to the first (`second-instance`) and quits.
- `notifications.cjs` shows notifications for expo-notifications' stand-in: right away, or for a reminder at its time, checked at least every minute (timers don't count sleep), while learnX runs; one more than 6 hours late is dropped. Windows and Linux have no subtitle, so the course leads the body there. A click shows the window and tells the page, which opens the item (`useNotificationTaps`). There are no action buttons.
- `fileShell.cjs` does what reaches outside learnX's folders, always through a dialog the user answers or the system: Open in Default App (`shell.openPath`), Show in Folder, Save As (a save dialog and a copy), saving text (the .ics export), picking a folder for Export (which `files.cjs` then lets the page write in, `grant`), and picking files to submit (copied into `Caches/picked`). It also serves downloads to the file preview at `app://files/<cache|document>/<path>`, an origin of its own, so a downloaded file never reaches the app's page or its bridge, and only PDFs and pictures (no SVG).
- `menus.cjs` shows a native menu for the page (`menu:popup`, `learnx.menu`): a card's context menu. It keeps only the item fields the page may set and resolves with the chosen item's id.
- Tests are in `__tests__`, run by Jest's `tooling` project and typed by `scripts/tsconfig.json`.

## Logging in

- A first login opens Tsinghua's login page in a web view, as `screens/SSO.tsx` does on the phone: the injected script fills in the username and password, two-factor happens on the page, and the form it captures (with the device fingerprint) is saved, encrypted, once Web Learning's roaming URL is reached. The confirmation before it is a Fluent dialog, as every alert is.
- An expired session is found as on the phone: thu-learn-lib reads a 403 or a final URL on `login_timeout` (the main process records it while following redirects) and signs in again with the saved login. `clearLoginCookies` removes the SSO cookies from the session before each login; logout clears every cookie in it (`clearSessionCookies`), the saved login and the downloads.

## The page (`src/web`)

- Web variants use platform extensions (`.web.ts`, `.web.tsx`), which Metro picks over the iOS file. Metro tries every platform for one extension before the next, so a `.web.tsx` file loses to a `.ts` base file: give a variant the base file's extension (`modules/toast/index.web.ts` re-exports `src/web/packages/toast.tsx`).
- `index.web.js` renders the app into the page inside `web/FluentRoot` (Fluent's light or dark theme, `web/fluentTheme`, with the brand ramp in `theme/electron`; the app's own colors come from the same palette). `polyfills.web.js` sends the page's http(s) requests through the main process (`web/fetch`), fills in `PlatformColor` and `DynamicColorIOS` as CSS variables that follow the system's appearance (`web/systemColors`), and makes `Alert.alert` a Fluent dialog (`web/alert`; React Native Web's does nothing).
- Components: each `@expo/ui` pair has a `.web.tsx` variant with Fluent UI (`Form.web.tsx` lays rows out as Windows 11 Settings' cards); its props come from the pair's `.shared.ts`, never a value import from `./X`. Icons are Fluent System Icons: `helpers/systemIcons` names each one (`windows`) and `web/fluentIcons` imports them one by one, from `@fluentui/react-icons/svg/<name>`. Never import icons from the package's index: it has every icon (about 20 MB) and the web build doesn't tree-shake, which is also why Metro resolves Fluent's own imports of it to `web/packages/fluentReactIcons` (regenerate its list when Fluent adds icons; a test checks it). Fluent copies `FluentProvider`'s classes onto its portals, so the root's size is a style, and a tooltip on a control with its own label uses `relationship="inaccessible"` (a `description` tooltip stays mounted).
- Navigation: the tab navigator's stand-in (`web/packages/navigationPane`) is Windows' navigation pane, drawn into `navigation/WindowFrame.web.tsx`'s slot at the window's edge (a Fluent `Portal`), beside the JS split view: expanded from 1008 px wide, a rail of icons below, and Settings as a tab at its foot (`settingsTab` in `navigation/layout`). Headers title the page at the start (`HeaderTitle.web.tsx`, `stackScreenOptions`); Search's box is `HeaderSearch`.
- Desktop input: `modules/menus/index.web.tsx` turns F5 / Ctrl+R, Ctrl+F, Ctrl+, and Alt+↑/↓ into the menu bar commands `useAppCommand` listens to, and its `ContextMenuView` shows a card's actions as a native menu on right-click (or the menu key, Shift+F10), as buttons while the pointer is on the card (cards don't swipe here), and moves focus between cards with ↑/↓. Header menus and form rows that ask are Fluent menus.
- Packages with no web build, or one that can't run there, resolve to the files `src/web/aliases.json` names, on web only (`metro.config.js`): expo-sqlite's kv-store, expo-secure-store and the cookie manager on the bridge, and stand-ins (`src/web/packages`) for react-native-webview (`WebView.tsx`, see `webviews.cjs`; a `file:` source shows in `web/FilePreview` instead), expo-file-system (files over IPC, see `files.cjs`; picking a folder asks in the system's dialog), react-native-pdf (`web/FilePreview`: Chromium's PDF viewer in a frame on `app://files/`), expo-notifications (`notifications.ts`, see `notifications.cjs`: allowed wherever the system shows them, with no prompt), expo-task-manager and expo-background-task (the main process's timer runs the registered task), expo-document-picker and expo-image-picker (the system's open dialog), the native tab bar (the navigation pane) and, minimal, for SwiftUI views and modifiers (for what has no `.web.tsx` variant) and react-native-share (no share sheet: File detail has Open in Default App, Save As, Show in Folder and Copy Link instead). They're tested in `src/web/__tests__` with a fake bridge (`test-utils/mocks/electronBridge`). What renders Fluent UI is tested in Jest's `web` project (`__tests__/web/` folders): React Native Web and Fluent in jsdom, with Testing Library for React.
- What `index.js` starts runs as on the phone, with the stand-ins above: the background task, the surfaces (only the deadline and class reminders do anything: widgets, Spotlight and App Intents have no module here, and calendar sync is off), and assignment changes. Only notification actions have a no-op `.web.ts` variant. Settings › Calendar only exports an .ics file, built from learnX's own data (`services/calendar/desktopExport`), since Windows and Linux have no calendar on the device to sync to; Setup leaves calendar sync out. A submission's attachment goes up as bytes through the main process (`data/source`, no upload progress), and a file dragged onto the submission screen becomes the attachment (`components/FileDropTarget.web.tsx`).

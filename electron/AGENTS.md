# The Electron app (Windows and Linux)

An Electron app around a React Native Web build of the app's own code, drawn with Fluent UI React v9 so it looks like a Windows app. Its web build and E2E tests are required pull request checks (`Electron / Web build`, `Electron / E2E tests (Linux)` and `(Windows)`), and it's released with the phones, on the same GitHub release, though a mobile release never waits on it. It has the mock and live logins (the SSO page for a first login, re-login when the session expires, logout), web pages and notice bodies, downloads, the Windows UI, and the desktop services: previewing, opening and saving files, picking and dropping files to submit, notifications and reminders, the tray with the background sync, Start at login, the .ics export and the Jump List; packaging and updates are below.

## Running it

- `pnpm electron` exports the web build (`expo export -p web`) to `build/electron/web` and opens it in Electron; `--skip-export` reuses the last export. The first run downloads Electron itself into this package's `node_modules`: `pnpm install` skips Electron's download script (`allowBuilds` in `pnpm-workspace.yaml`), so mobile installs never fetch it.
- On Linux a dev run passes `--no-sandbox` (`dev.ts`): the downloaded Electron's `chrome-sandbox` isn't setuid root and Ubuntu 24.04 and later block the user namespaces the sandbox needs otherwise, so it would abort. Packaged builds keep the sandbox.
- In development everything Electron writes stays in `build/electron/data`, and the saved login stays out of the system's key store: `--use-mock-keychain` on macOS, Chromium's own key on Linux (`--password-store=basic`, which `secrets.ts` accepts only in a dev run), so dev runs and the E2E tests keep their login with a locked keyring or none (CI). On a Mac the runner opens `build/electron/learnX.app` (`macDevApp.ts`), a copy of the downloaded `Electron.app` renamed as `@electron/packager` would: `learnX` with the id `io.robertying.learnXElectron`, helpers `learnX Helper` (`(GPU)`, `(Renderer)`, `(Plugin)`) with the id `io.robertying.learnXElectron.helper`, and the Mac Catalyst app's icon compiled by `actool` from `ios/learnX/AppIcon.icon`, signed ad hoc. So the Dock, the menu bar, Activity Monitor and LaunchServices say learnX, and the preferences it writes are `io.robertying.learnXElectron`'s. It's made again when Electron's version or the icon changes (`learnX.app.json` next to it). With the executable renamed, `app.isPackaged` is true (Electron only looks at the executable's name), so `main.ts` takes a run that opened its folder (`process.defaultApp`) as a dev run too. Windows and Linux run the stock Electron: there, `setAppUserModelId` and the app name do what's possible without packaging.
- `pnpm electron:clean` (`clean.ts`) removes what dev runs leave on a Mac and prints each item: the dev data folder; the preferences of `io.robertying.learnXElectron`; folders under `~/Library` (Application Support, Caches, HTTPStorages, Saved Application State, Logs, WebKit) named after that id or `learnX`; LaunchServices' entries for this checkout's `learnX.app` and `Electron.app` (`lsregister -u`); and keychain items for "learnX Safe Storage". It never touches the Mac Catalyst app's `io.robertying.learnX`, nor what the stock `Electron.app` keeps for every unpackaged Electron app (`com.github.Electron`, "Electron Safe Storage"), and leaves `learnX.app` for the next run (`build/` goes with the checkout). Run it after testing.
- `--capture <dir>` lets the page save window captures (`await learnx.capture('name')`, `webContents.capturePage` with background throttling off, web views included). A window's capture leaves its web views out, so each is saved next to it as `<name>-webview-<n>.png`. Pass `-- --remote-debugging-port=9222` to drive the window over the Chrome DevTools Protocol (web views are targets of their own there; `Emulation.setDeviceMetricsOverride` tries narrower window sizes) and `--inspect=9229` for the main process. `LEARNX_COLOR_SCHEME=dark` (or `light`) sets the window's appearance whatever the system's (`nativeTheme.themeSource`), which reaches `prefers-color-scheme` and so the app's theme; DevTools' color scheme emulation doesn't.
- A dev run never posts system notifications (on a Mac they'd leave a learnX entry in System Settings › Notifications): it logs each (`[notification] title | subtitle | body`) and the page shows it as a toast. `LEARNX_NOTIFICATIONS=system` posts real ones; check those on Windows. With `--inspect`, `learnxDev.notifications.at(-1).click()` clicks the last one (its `options` are what it showed), `learnxDev.tray()` is the tray and `learnxDev.trayMenu()` its menu; the E2E tests use them too. A dev run never changes Start at login either (it logs what it would have done) unless `LEARNX_ALLOW_LOGIN_ITEM=1`; don't set that on the Mac you develop on.
- The file preview's PDF viewer is a frame of its own that `learnx.capture` leaves out; capture the window over the DevTools Protocol (`Page.captureScreenshot` on the page's target) to include it.
- `LEARNX_LAUNCH_OPTIONS` (JSON) gives the app a test run's launch options (`src/services/launchOptions`) as its root props, as Android's launch extras do. The live test login (`liveUsername`, `liveFingerprint`) also needs `TEST_LOGIN=1` for the export.

## Main process

- It's TypeScript with no build step: Electron's Node (24, in Electron 45) strips the types from `main.ts` and the modules it imports as it loads them, as Node 26 does for the dev and packaging scripts (`pnpm electron` runs `node electron/dev.ts`). So the code is ES modules (`"type": "module"` in `package.json`), imports name the `.ts` file, and only syntax Node can strip is allowed (no enums, namespaces or parameter properties: `erasableSyntaxOnly`), with `import type` for types (`verbatimModuleSyntax`). `tsconfig.json` here types it, strictly, with Node's types. The preloads are the exception: a sandboxed preload runs without Node's module loader, so `preload.cts` and `webviewPreload.cts` are CommonJS, and `preloads.ts` strips their types with Node's `stripTypeScriptTypes` into `build/electron/preloads/*.cjs`, as a dev run starts (so it never runs a stale copy) and when packaging. `preload.cts` is typed by the page's own declaration of the bridge (`src/web/bridgeTypes.ts`), so the two sides can't drift apart.
- `main.ts` names the app learnX (`app.setName`, `productName`), with the app id `io.robertying.learnXElectron` (`setAppUserModelId` on Windows), named as a top-level target like `io.robertying.learnXTests`: `io.robertying.learnX.<name>` is for the iOS app's extensions, and the iOS bundle id is the Mac Catalyst app's. It serves the web build from `app://learnx/` with a content security policy (`appOrigin.ts`), keeps the window on the app (links open in the browser), and registers nothing with the system. The window has a saved session of its own (`persist:learnx-app`), the only one that serves `app://`, so a page in a web view can't load the app's scripts or a download's preview; `app://` keeps compiled code there (`codeCache`), so later launches don't compile the 7.7 MB web build again: the session is saved to disk, in its own partition folder, since Chromium keeps no code cache for an in-memory one. The window shows once its page has drawn (`ready-to-show`), except on Linux, where it shows at once in its background color: under Wayland a window that was never shown gets no frames, so a page that first draws after a large script (the web build) never draws and `ready-to-show` never comes. It opens where it was last time, at its zoom (`windowState.ts`; one saved maximized is maximized only as it's shown, so Start at login keeps it in the tray on Windows, the only platform that starts it hidden, with `--hidden`), a crashed page is loaded again (three times at most), and a packaged build has no application menu (Electron's default one has Developer Tools and Force Reload); dev runs keep it. With no menu, the window handles Ctrl+= / Ctrl+- / Ctrl+0 (Cmd on macOS) itself (`zoomForKey`).
- The page runs sandboxed and context-isolated; `preload.cts` exposes `window.learnx`, and every IPC handler checks that the call comes from the window's main frame on `app://learnx/` (`fromApp`), never from a web view or a frame; `__tests__/main.test.ts` checks every channel the preload uses against that, on a stand-in for Electron. Web views may only go full screen and write to the clipboard, on the sites they may show (`webviewPermission`); nothing else is granted.
- What the main process and the page share is kept once in `src/constants` (`electronFileTypes.json`, `webviewPartition.json`): `shared.ts` reads it from the checkout, and from a copy in a packaged app (`packageConfig.ts`).
- `net.ts`: requests to Tsinghua's sites (and courseX) run here with `net.request` and the window session's cookies, following redirects itself to record the final URL (Electron's `net.fetch` leaves `Response.url` empty). Other hosts, and redirects to them, are refused. A request fails after a minute without hearing from the server (before the response and between its pieces; five minutes to send an upload first).
- `webviews.ts`: the page's web views (`<webview>`, the `react-native-webview` stand-in). Each is hardened as it attaches: the window's session (`persist:learnx`, so it shares the cookies), the sandbox, context isolation and learnX's own preload (`webviewPreload.cts`, which gives the page `window.ReactNativeWebView.postMessage` and runs the injected scripts), whatever its attributes ask; a page may only turn JavaScript off. Every top-level load waits in `webRequest.onBeforeRequest` while the page decides (`onShouldStartLoadWithRequest`, `originWhitelist`), so a form's POST goes ahead as sent; a load the page allows off Tsinghua's sites, courseX and learnX's GitHub pages opens in the browser instead, as do new windows and mail links. HTML loads as a data URL at its base URL, as the phones' `loadHTMLString` does, unless it's too long for one (Chromium refuses URLs over 2 MB: a notice with a pasted picture, or a long Chinese one): then `loadHtml` loads the base URL and answers that one document request with the HTML through the web view's own DevTools protocol (`Fetch`), touching nothing else's requests; a second one in the same web view ends the first.
- `files.ts`: learnX's own files, under `Files/Caches` and `Files/Documents` in the app's data folder, for expo-file-system's stand-in; every path must lie in them, or, for what an export does (looking in it, making folders, copying the app's files in, never reading, changing or deleting what's there), in a folder the user picked for it in the last 10 minutes of use (`grant`). A dropped file is copied in with `append`, 4 MB at a time. Downloads run here with the session's cookies, from Tsinghua's sites and courseX (and the mock account's files on GitHub), and fail on a status other than 2xx as expo-file-system's do, so thu-learn-lib's download check and re-login work as on the phone. On Windows a finished download gets the `Zone.Identifier` stream a browser writes, so Windows, SmartScreen and Office warn as they do for a browser's download.
- The app's data folder is Electron's `userData`, except on Windows, where `main.ts` moves it to the local profile (`%LOCALAPPDATA%\learnX`): Electron's default, `%APPDATA%`, roams to other PCs at every sign-in on domains with roaming profiles, downloads and all. Uninstalling (not updating) removes it, Start at login's Run entry and electron-updater's downloads (`installer.nsh`), and `%APPDATA%\learnX` (`deleteAppDataOnUninstall`). On Linux it's `~/.config/learnX`, which deleting the AppImage or removing the .deb leaves; the privacy policy says so.
- `fileStore.ts`: key-value storage as one file per key under the app's data folder (capital letters escaped, so keys that differ only in case don't share a file on NTFS or APFS), written to a temporary file, flushed and renamed over the old one; while Windows reports the file busy, the rename is tried again later (for about five seconds, without blocking the main process), with the newest value written meanwhile. The page sends its writes without waiting, so one that fails is logged (`loggedWrites`), never thrown. `secrets.ts` keeps the saved login in it encrypted with `safeStorage`'s asynchronous APIs, and refuses to save where the system has no key of its own: no encryption at all, or on Linux a value not encrypted with the keyring's key: one Chromium tags `v10`, its own fallback key (without a keyring, or after its unlock is cancelled), is refused; the Secret Service's and KWallet's `v11`, or any other tag (the Secret portal's), is kept. The synchronous APIs ask the keyring on the main process's thread, so with GNOME's login keyring locked (as an automatic login leaves it) they would block the main process, and the window, for as long as its unlock prompt is up; only the asynchronous ones are used: the check (`isAsyncEncryptionAvailable`) waits for the prompt off that thread. Meanwhile a login goes on at once and is saved once the keyring opens (kept in memory until then), and a launch waits up to 30 seconds for it before going on without the saved login, which stays for the next launch.
- `system.ts` is what's around the window, set up by `main.ts`. Closing the window hides it on Windows (learnX stays in the tray) and macOS (in the Dock, where Quit ends it); on Linux it quits, since GNOME shows no tray icons without an extension and nothing tells whether one would show (`closesToTray`). Signing out or shutting down closes it for real (`session-end`, the power monitor's `shutdown`). The tray's menu has Open learnX, Check for New Items (a background sync now; not "Sync", which in learnX is the calendar's and Reminders', nor "Check for Updates", which reads as app updates) and Quit, labeled in the page's language (`system:setLabels`), with the gap between Chinese and Latin text typed in on Windows and Linux, whose menus, dialogs and notifications draw none (`web/systemText`). The background sync runs on a timer here, every 15 minutes as the page registers it (`web/packages/backgroundTask`), and after the computer wakes, so a hidden window's slowed timers don't hold it back; the page runs `services/background`. Start at login (`app.setLoginItemSettings`, Windows and macOS; on Windows with `--hidden`, which starts in the tray) is read for Settings and written only when its switch changes, read with the same arguments it's written with (Windows reports a Run key whose arguments differ as off). On Windows the Jump List (`app.setUserTasks`) has Today and Schedule, which launch learnX with `--learnx-open=<screen>`: the app holds a single instance, so a second launch hands its arguments to the first (`second-instance`) and quits.
- `language.ts` is the app's own language, in Settings › Language on Windows and Linux only, which have no per-app language (a Mac dev run offers it with `LEARNX_LANGUAGE_SETTING=1`, as the E2E tests do; the Mac, iOS and Android use the system's per-app language): Follow System, 简体中文 or English, saved in the app's data folder. A choice takes effect at the next launch, where `main.ts` sets it as Chromium's `--lang` before the app is ready, so the page (`helpers/i18n`), its dates and mock data, and the tray and dialogs, which follow the page, all switch with it and nothing else reads it. Choosing one asks to restart now (`app.relaunch()`, then quit) or later.
- `notifications.ts` shows notifications for expo-notifications' stand-in: right away, or for a reminder at its time, checked at least every minute (timers don't count sleep), while learnX runs; one more than 6 hours late is dropped. Windows and Linux have no subtitle, so the course leads the body there: on its own line on Windows, before a " · " on Linux, where GNOME's banner shows the body as one line. A click shows the window and tells the page, which opens the item (`useNotificationTaps`). There are no action buttons.
- `fileShell.ts` does what reaches outside learnX's folders, always through a dialog the user answers or the system: Open in Default App (`shell.openPath`; a file that would run as a program, by `electronFileTypes.json`'s `runnable`, opens only after a system dialog with Cancel first, in the page's language), Show in Folder, Save As (a save dialog and a copy), saving text (the .ics export), picking a folder for Export (titled in the page's language, which `system:setLabels` sends with the tray's labels, since GTK's own title says "Open File"; `files.ts` then lets the page write in it, `grant`), and picking files to submit (copied into `Caches/picked`, which is cleared at launch: a draft keeps its own copy). It also serves downloads to the file preview at `app://files/<cache|document>/<path>`, an origin of its own, so a downloaded file never reaches the app's page or its bridge, and only PDFs and pictures (no SVG).
- `menus.ts` shows a native menu for the page (`menu:popup`, `learnx.menu`): a card's context menu. It keeps only the item fields the page may set and resolves with the chosen item's id.
- Tests are in `__tests__`, run by Jest's `tooling` project and typed by `scripts/tsconfig.json`. Jest loads the main process as Node does (`babel/jest-node-esm.js`: `import.meta`, `import()` through Jest's registry, and Node's default import of a CommonJS module), and the preloads as they ship, stripped by Node (`jest/stripTypes.js`). The main process's files count in Jest's coverage, except the dev-only scripts (`dev.ts`, `clean.ts`, `package.ts`, `webExport.ts`, `macDevApp.ts`, `devTraces.ts`, `electronApp.ts`).

## Packaging and updates

- `pnpm electron:package` (`package.ts`) exports the web build and runs electron-builder with `packageConfig.ts` into `build/electron/dist/`, packaging `main.ts` and what it imports (`mainProcessFiles`) as TypeScript, and the stripped preloads: one NSIS installer for Windows x64 and arm64 (`learnX-windows-v<version>.exe`, per user only, never in Program Files, so updates install without elevation, with a choice of folder; `installer.nsh`), and an AppImage and a .deb for Linux x64 and arm64 (`learnX-linux-<arch>-v<version>.AppImage` / `.deb`; electron-builder writes x64 as `x86_64` and `amd64`), named like the Android APKs, with the `latest*.yml` update files and `.blockmap`s; `--win` or `--linux` builds one. `--dir` builds only the unpacked apps (`win-unpacked`, `linux-unpacked` and their arm64 twins). A Mac (Apple silicon with no Rosetta too), Windows or Linux builds both platforms' installers: the toolsets in `packageConfig.ts` (NSIS 3.12's bundle, the AppImage tools) and fpm, for the .deb, have arm64 macOS builds; the legacy NSIS toolset's `makensis` is Intel-only (spawn error -86 without Rosetta), and a test keeps it out. Never macOS (the Mac has the Catalyst app). Unsigned: Windows SmartScreen asks once (More info, then Run anyway). The .deb needs a homepage (`extraMetadata.homepage`). The AppImage uses electron-builder's static runtime (`toolsets.appimage`), which needs neither libfuse2 (not installed since Ubuntu 22.04) nor `libz.so` (the legacy arm64 runtime linked it, so it only started with `zlib1g-dev` installed); its AppRun turns Chromium's sandbox off (`--no-sandbox`) only where unprivileged user namespaces are blocked, as on Ubuntu 24.04 and later, which an AppImage can't change (the .deb installs an AppArmor profile that allows them): the release notes point Ubuntu users to the .deb. electron-builder downloads Electron and its tools into `build/electron/cache`. No Wine is needed (the .exe's icon and version info are written in JS). CI's `Electron / Installers` checks that both platforms still build, on their own runners, by hand only (Actions › Electron › Run workflow; not a required check); its builds are never released. Releases are built, signed and uploaded by hand with fastlane's `electron` lanes (the release skill).
- Icons: `icons/icon.ico` (Windows: 16, 20, 24, 32, 40, 48, 64, 96, 128 and 256, the 256 as a PNG) and `icons/icon.png` (Linux, 512, from which electron-builder makes the hicolor sizes), which the window and the tray use in dev runs too. They're made from the Icon Composer source, `ios/learnX/AppIcon.icon`, by `node electron/icons/generate.ts` on a Mac with Xcode: Icon Composer's CLI (`ictool`, found through `xcode-select -p`) exports each size as macOS draws it (the squircle with its Liquid Glass shading, edge to edge), at about 92% of the size, and the script centers it on a transparent canvas, since Windows and Linux don't mask icons, after `sips` turns its Display P3 into sRGB. Run it after the icon changes and commit the outputs: Windows and CI can't make them. The Mac dev app's icon is `actool`'s (`macDevApp.ts`).
- Identity: the app id `io.robertying.learnXElectron`, product name learnX, the company Rui Ying and the file description learnX on Windows, and on Linux the `learnx` executable with `learnx.desktop`, whose `StartupWMClass` is the window's class, `learnx` (Electron takes Wayland's app_id and X11's class from `desktopName`; `syncDesktopName`).
- Version: `buildInfo.ts` reads `package.json`'s version and the Xcode project's build number, which `pnpm bump` keeps for every platform; the config writes them into the packaged app's `package.json` (`version`, `buildNumber`) and Windows' file version (`19.0.0.4544`). The page reads them through `learnx.appInfo()` (the `expo-application` stand-in, `src/web/packages/application.ts`), so Settings › About shows `19.0.0 (4544)`, as does the About panel (`app.setAboutPanelOptions`; on a Mac the build number goes in its build version, which macOS puts in brackets itself, and which would otherwise be the dev app's bundle version: Electron's).
- Updates (`updater.ts`, with `electron-updater`): a packaged build installed by NSIS, or run as an AppImage, checks 10 seconds after launch and every 4 hours, downloads in the background and installs when the app quits; once one has downloaded, Settings shows it on top (`hooks/useAvailableUpdate.web.ts`) and its row offers Restart (`useUpdateInstaller.web.ts`, `learnx.updates.install()`). A .deb doesn't install updates itself (that needs an administrator's password), so it only checks (`notify` mode, `package-type` says it's a .deb): once a newer version's update file is out and verified, Settings shows it on top, and its row offers that version's .deb on the mirror (`learnX-linux-amd64-v<version>.deb`, `debFileName`) to download instead of Restart, as Google Play's Android builds open the APK. A dev run tries it with `LEARNX_UPDATE_MODE=notify`. Updates come from the TUNA mirror's copy of the latest GitHub release (`LatestRelease/`, the Android APKs' too; the URL is in `src/constants/updateMirror.json`, which `helpers/update` also reads), through electron-updater's generic provider (`publish` in `packageConfig.ts`, written into the app's `app-update.yml`): it reads `latest.yml` (Windows) or `latest-linux[-arm64].yml` there, so a release without them offers no update, and downloads the installer named in it, in ranges when a `.blockmap` allows. electron-updater checks the download's SHA-512 against it, and reads it only through `updateSignature.ts`'s provider, which refuses an update file without a valid detached Ed25519 signature next to it (`latest.yml.sig`, base64): signed at release time on the maintainer's Mac with learnX's Electron update key (`scripts/release/sign-electron-update.mjs`, the release skill), whose public half the packaged app carries (`certs/electron-public-key.pem`). A missing, unreadable or wrong signature, or one by another key, means no update, logged as `[updater] failed: latest.yml refused: …`. So the mirror alone can't make an install run anything (the installers themselves are unsigned), and installing on quit only ever installs a verified update. The mirror copies a release on a schedule, so a check can find the new `latest.yml` before the installer: the download fails (a 404 or a checksum mismatch), which is only logged, and another check runs half an hour later. File names have no spaces (`packageConfig.ts`; a test checks), since GitHub turns spaces in asset names into dots and the links in `latest.yml` would break.
- Signing updates: the key is learnX's own Ed25519 key for Windows and Linux updates, not the over-the-air one. Its public half is `certs/electron-public-key.pem`, and its private half is in the maintainer's 1Password, never in the repo. A key file whose first line says `PLACEHOLDER` (one nobody holds the private half of) is refused by `sign-electron-update.mjs` and by `pnpm electron:package` (`placeholderKeyProblem`), CI's `Electron / Installers` included, except for `--dir`, a test build's `--update-url` on localhost and `--allow-placeholder-key` (installers never to be released); a test checks that the committed key is a real Ed25519 key. Tests and dev runs sign with throwaway keys, trusted through `LEARNX_UPDATE_PUBLIC_KEY`. To rotate the key, make a new one in the repo root with Node's own crypto (macOS's LibreSSL can't make Ed25519 keys):

  ```bash
  node -e "const c=require('crypto'),fs=require('fs');const k=c.generateKeyPairSync('ed25519');fs.writeFileSync('learnx-electron-private-key.pem',k.privateKey.export({type:'pkcs8',format:'pem'}),{mode:0o600});fs.writeFileSync('certs/electron-public-key.pem',k.publicKey.export({type:'spki',format:'pem'}))"
  ```

  Then put `learnx-electron-private-key.pem` (the private key) in 1Password in place of the old one, delete the file, and commit `certs/electron-public-key.pem`. Installs only trust the key they were built with, so the first release with a new key reaches users only through a download, not an update: rotate only if the private half leaks.

- Trying updates without publishing: `node electron/updateServer.ts <dir>` serves the folder `<dir>` on `http://localhost:8299/` as the mirror serves `LatestRelease/`, byte ranges too. Point a test build at it (`pnpm electron:package --win --version 19.0.1 --update-url http://localhost:8299/`), or a dev run with `LEARNX_UPDATE_URL=http://localhost:8299/` (dev runs check only then, and download into the data folder's `updates`, not the system's caches folder), and copy a build's installer, `latest*.yml` and `.blockmap` into the folder, with the update file's signature, to release it. A dev run trusts the public key at `LEARNX_UPDATE_PUBLIC_KEY` instead of `certs/electron-public-key.pem`, so a throwaway key can sign there (`updateSignature.signUpdateFile`, as `updates.e2e.ts` does); a test build always trusts the committed one. A Mac dev run gets as far as the download: Squirrel.Mac, which installs on macOS, refuses an unsigned app.

## E2E tests (Playwright)

- `pnpm e2e:electron` runs the tests in `e2e/` (`*.e2e.ts`; Jest skips the folder) with `@playwright/test`'s Electron support, as configured in `playwright.config.ts`: one worker locally, since each test launches a whole app, and one per core on CI; 90 s per test; on failure a trace and a screenshot in `build/electron/e2e/results` (`pnpm exec playwright show-trace <trace.zip>`); on CI one retry (for its trace) and an HTML report, a test that passes only on its retry fails the run (`failOnFlakyTests`), and the whole run stops after 15 minutes (`globalTimeout`), so a run that crawls still ends with its report and traces before the job's own limit cancels it. The whole run takes about 4 minutes, a minute of it the timeout test's server waits (`errors.e2e.ts`). Append a file or `-g <title>` to run some (`pnpm e2e:electron tray`). They need the web build in `build/electron/web` (from `pnpm electron` or `pnpm electron:package`) exported with the mock login in `.env`, and the network: the mock account's files download from GitHub and `sso.e2e.ts` opens id.tsinghua.edu.cn, as the flows do (its tests are tagged `@network` and skip themselves when it doesn't answer, as from CI's runners abroad at times). CI runs them in `.github/workflows/electron.yml` on every pull request that can affect the app, both required: `E2E tests (Windows)`, and `E2E tests (Linux)`, one app per core (`workers` in `playwright.config.ts` on CI; each test has its own data folder and ports, and on Linux each worker its own Xvfb display, from `e2e/fixtures.ts`, since on a shared one the other workers' windows opening over a test's window end its hover), then `window.e2e.ts` once more in the same job under Weston's headless Wayland compositor (no X display, `XDG_SESSION_TYPE=wayland`), where a window that never shows gets no frames: it checks that the window is visible and that a captured frame has the page in it. Under X11 a window draws whether it shows or not.
- E2E runs never come to the front: the fixture sets `LEARNX_E2E`, and the dev run then never focuses its window or brings it forward (`present` in `system.ts` records that it would, which `main.windowVisible()` reads; on Windows and Linux it shows the window behind the others without focus, and on a Mac not at all), renders it in the background (`backgroundThrottling` off) and, on a Mac, runs as an accessory app with no Dock icon (the dev app starts as one, `LSUIElement` in `macDevApp.ts`, and other dev runs make themselves regular apps). A window that was never shown hardly draws on Windows and Linux: under Wayland it gets no frames, so its page never draws, and on Windows about two a second, so animations and Playwright's waits for a still element crawl (every test took several times as long, and the run outlasted its job). `window.e2e.ts` checks that the window shows and draws at full rate there. Playwright drives it over the DevTools Protocol, which needs no window in front; a test asserts what the app asked for, not what the OS shows, except `window.e2e.ts`.
- `e2e/fixtures.ts` gives each test a fresh data folder (`dataDir`, deleted after it) and `app` (an `ElectronApplication`), `window` (its window), `main` and `login`. `app` is a dev run of the checkout (learnX.app on a Mac, `electronApp.ts`, which `pnpm electron` uses too) on that folder, with secrets out of the keychain, update checks off (`LEARNX_NO_UPDATES`, unless the test sets `LEARNX_UPDATE_URL`) and the launch options of the Maestro flows' `launchApp` (`{ mockLatency: 'none' }`; a test sets others with `test.use({ appLaunchOptions })`, arguments and environment with `appLaunch`, the language with `language`, `--lang`). `relaunch({ launchOptions, args, env })` quits the app and starts it again on the same folder, as a flow's `launchApp` does (the single-instance lock is in the folder, so one at a time). `LEARNX_E2E_APP=<executable>` tests a packaged app instead (`build/electron/dist/win-unpacked/learnX.exe`, `linux-unpacked/learnx`): it takes no launch options, and Chromium's `--user-data-dir` and `--use-mock-keychain` keep it to the throwaway folder; tests that need a dev run's hooks skip themselves there (`test.skip(!!packagedApp, …)`): the failures in `errors.e2e.ts` (launch options), `notifications.e2e.ts` (logged notifications), the tray's menu in `tray.e2e.ts` (and its labels in `language.e2e.ts`, which checks the rest) and `updates.e2e.ts` (the update server). `login()` is `subflows/login-form.yaml`: Continue on the welcome page, the mock account from `.env`, then Not Now on the set-up page. Before the run, `e2e/setup.ts` downloads Electron (and builds learnX.app on a Mac) once, so parallel workers don't race to do it. After the run, `e2e/teardown.ts` removes what learnX.app left on a Mac (`clean.ts --keep-data`, which keeps the dev login in `build/electron/data`).
- `main` (`e2e/mainProcess.ts`) stands in, inside the app's main process (`electronApp.evaluate`), for what Playwright can't click, installed before each test starts so nothing reaches the system, and records what the app asked for (`main.record()`): `dialog.showOpenDialog` / `showSaveDialog` / `showMessageBox` answer with `main.stub({ open, save, messageBox })` (cancelled by default; call it again to change the answers); `Notification`s, `shell.openPath`, `openExternal` and `showItemInFolder` are recorded instead; `app.setLoginItemSettings` is recorded and kept in the data folder, where `getLoginItemSettings` reads it back as Windows does (on only when asked with the same arguments), across a relaunch; `app.relaunch` is noted in the data folder (`e2e-relaunched`) instead of starting a learnX the test doesn't drive; a native menu (a card's context menu) is recorded instead of shown, and `main.chooseMenuItem(label)` clicks its item. Through the dev run's `learnxDev` (system.ts) it reads and chooses the tray's menu (`trayLabels`, `chooseTrayItem`) and reads and clicks the notifications a dev run logs (`shownNotifications`, `clickNotification`); it also closes the window as its close button does (`closeWindow`: to the tray, or on Linux quitting) or hides it (`hideWindow`, as closing does where learnX keeps running), hands over a second launch's arguments (`secondLaunch`, as a Jump List task) and records electron-updater's quit-and-install (`stubInstall`). The stand-ins patch Electron's modules, so main-process code must call them as `dialog.showOpenDialog(…)`, not through a copy taken at startup.
- `e2e/steps.ts` holds the subflows' counterparts (`openTab`, `openCard`, `cardAction`, `filter`, `toggle`, `search`, `openSettingsPage`, `goBack`). The window (1200 × 800) shows the split views, so details, settings pages and what opens as a sheet on the phone (the submission page, courseX) open beside their list, as on an iPad, behind React Navigation's back link (`<screen>, back`).
- Selectors, as the Maestro flows use them: `getByTestId` for `testID`s (React Native Web renders them as `data-testid`: `tab-notices`, `login-username`, `settings-list`), `getByRole` and `getByText` for the rest. `e2e/maestroEnv.ts`'s `text('MOCK_NOTICE')` or `text('T_todayDueSoon')` is the flows' `${MOCK_NOTICE}` (the same English|Chinese alternation, from `scripts/e2e/e2e-env.mjs`, which also prints every `'T_<key>'` the tests name; `{param}` placeholders match anything), and `exact(key)` matches a whole label. `scripts/__tests__/e2eEnv.test.ts` checks the tests' values as it does the flows'. Tabs and split panes stay mounted when hidden, so match what shows: `steps.ts`'s `shown()` / `byId()` (`.filter({ visible: true }).first()`). No fixed waits: Playwright's assertions and `expect.poll` wait for what a test needs.

## Logging in

- A first login opens Tsinghua's login page in a web view, as `screens/SSO.tsx` does on the phone: the injected script fills in the username and password, two-factor happens on the page, and the form it captures (with the device fingerprint) is saved, encrypted, once Web Learning's roaming URL is reached. The confirmation before it is a Fluent dialog, as every alert is.
- An expired session is found as on the phone: thu-learn-lib reads a 403 or a final URL on `login_timeout` (the main process records it while following redirects) and signs in again with the saved login. `clearLoginCookies` removes the SSO cookies from the session before each login; logout clears every cookie in it (`clearSessionCookies`), the saved login and the downloads.

## The page (`src/web`)

- Web variants use platform extensions (`.web.ts`, `.web.tsx`), which Metro picks over the iOS file. Metro tries every platform for one extension before the next, so a `.web.tsx` file loses to a `.ts` base file: give the base file the variant's extension (`modules/menus/index.tsx` beside `index.web.tsx`). Where the phones have nothing to vary, the base file is a no-op (`hooks/useLoginItem.ts` beside `useLoginItem.web.ts`). The root `AGENTS.md` says where Electron code goes.
- `index.web.js` renders the app into the page inside `web/FluentRoot` (Fluent's light or dark theme, `web/fluentTheme`, with the brand ramp in `theme/electron`; the app's own colors come from the same palette, through `theme/colors.web.ts`). `src/polyfills.web.js` sends the page's http(s) requests through the main process (`web/fetch`), fills in `PlatformColor` and `DynamicColorIOS` as CSS variables that follow the system's appearance (`web/systemColors`), and makes `Alert.alert` a Fluent dialog (`web/alert`; React Native Web's does nothing). `web/FluentRoot` also keeps one Tabster (Fluent's focus manager) for the app's lifetime: Fluent disposes of it with the last control that used it, and a dialog that was that control (the logout confirmation) took the page's `aria-hidden` restore with it. An alert asked for by a key press (Enter in the password field) ignores the keys already down as it opened until they're released, so that press doesn't also answer it through the button it focuses.
- Components: each `@expo/ui` pair has a `.web.tsx` variant with Fluent UI (`Form.web.tsx` lays rows out as Windows 11 Settings' cards); its props come from the pair's `.shared.ts`, never a value import from `./X`. Icons are Fluent System Icons: `helpers/systemIcons` names each one (`windows`) and `web/fluentIcons` imports them one by one, from `@fluentui/react-icons/svg/<name>`. Never import icons from the package's index: it has every icon (about 20 MB) and the web build doesn't tree-shake, which is also why Metro resolves Fluent's own imports of it to `web/packages/fluentReactIcons` (regenerate its list when Fluent adds icons; a test checks it). Fluent copies `FluentProvider`'s classes onto its portals, so the root's size is a style, and a tooltip on a control with its own label uses `relationship="inaccessible"` (a `description` tooltip stays mounted).
- Navigation: the tab navigator's stand-in (`web/packages/navigationPane`) is Windows' navigation pane, drawn into `navigation/WindowFrame.web.tsx`'s slot at the window's edge (a Fluent `Portal`), beside the JS split view: expanded from 1008 px wide, a rail of icons below, and Settings as a tab at its foot (`settingsTab` in `navigation/layout`). Headers title the page at the start (`HeaderTitle.web.tsx`, `stackScreenOptions`, which also has the title shorten before the buttons: React Navigation's JS header guesses their width) and space their buttons as a command bar's (`headerButtons`); Search's box is `HeaderSearch`, between Close and Filter.
- Keyboard and mouse: `modules/menus/index.web.tsx` turns F5 / Ctrl+R, Ctrl+F, Ctrl+, and Alt+↑/↓ into the menu bar commands `useAppCommand` listens to, and its `ContextMenuView` shows a card's actions as a native menu on right-click (or the menu key, Shift+F10), as buttons while the pointer is on the card (cards don't swipe here), and moves focus between cards with ↑/↓. Header menus and form rows that ask are Fluent menus.
- Packages with no web build, or one that can't run there, resolve to the files `src/web/aliases.json` names, on web only (`metro.config.js`), every one in `src/web/packages` (the folder holds nothing else; the page's own helpers are in `src/web`): expo-sqlite's kv-store, expo-secure-store and the cookie manager on the bridge, and stand-ins for react-native-webview (`WebView.tsx`, see `webviews.ts`; a `file:` source shows in `web/FilePreview` instead), expo-file-system (files over IPC, see `files.ts`; picking a folder asks in the system's dialog), react-native-pdf (`web/FilePreview`: Chromium's PDF viewer in a frame on `app://files/`), expo-notifications (`notifications.ts`, see `notifications.ts`: allowed wherever the system shows them, with no prompt), expo-task-manager and expo-background-task (the main process's timer runs the registered task), expo-document-picker and expo-image-picker (the system's open dialog), the native tab bar (the navigation pane) and, minimal, for SwiftUI views and modifiers (for what has no `.web.tsx` variant) and react-native-share (no share sheet: File detail has Open in Default App, Save As, Show in Folder and Copy Link instead). They're tested in `src/web/__tests__` with a fake bridge (`test-utils/mocks/electronBridge`). What renders Fluent UI is tested in Jest's `web` project (`__tests__/web/` folders): React Native Web and Fluent in jsdom, with Testing Library for React.
- What `index.js` starts runs as on the phone, with the stand-ins above: the background task, the surfaces (only the deadline and class reminders do anything: widgets, Spotlight and App Intents have no module here, and calendar sync is off), and assignment changes. Only notification actions have a no-op `.web.ts` variant. Settings › Calendar only exports an .ics file, built from learnX's own data (`services/calendar/electronExport`), since Windows and Linux have no calendar on the device to sync to; Setup leaves calendar sync out. A submission's attachment goes up as bytes through the main process (`data/source`, no upload progress), and a file dragged onto the submission screen becomes the attachment (`components/FileDropTarget.web.tsx`).

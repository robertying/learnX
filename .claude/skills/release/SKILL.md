# Releasing learnX

- [fastlane](https://docs.fastlane.tools) (`fastlane/Fastfile`) builds and uploads releases on a Mac. It and CocoaPods are in the `Gemfile`: run `bundle install` once (the Ruby in `.ruby-version`, e.g. Homebrew's), then `pnpm install` and `cd ios && bundle exec pod install` (the locked CocoaPods and `Podfile.lock`; not `pnpm pod:update`, which also updates pods) before building.
- A feature release gets What's New highlights before it's built: an entry for its version at the top of `releases` in `src/helpers/whatsNew.ts` (its types say what a row takes; mark rows that need the new native code with `minNative`, and rows only some platforms have with `platforms`). A bug-fix release gets none: it shows no What's New, and its notes are in Settings › Changelog.
- `pnpm bump major|minor|patch` or `pnpm bump x.y.z` sets the version and build number on every platform; `pnpm bump build` (or `pnpm bump` alone) is a rebuild of the same version. `scripts/release/bump.sh` says how the numbers are derived.
- If the release changes native code since the last one, also set the over-the-air runtime version in `app.json` to the new version and record it in `ota-fingerprint.json` (CI's "Runtime version" check says when, and prints the values; "Over-the-air updates" in `AGENTS.md`). A JS-only release keeps it. The build lanes refuse to build with the placeholder update URL in `app.json`.
- `bundle exec fastlane <ios|mac|android> build` builds into `build/release/v<version>/` without uploading anything: the store binaries, the self-updating APKs with `latest.json` ("Updating the Android app" in `modules/AGENTS.md`), and the JS source map of each build in `sourcemaps/`. Crashlytics doesn't symbolicate JS, so keep these maps: `bundle exec fastlane symbolicate` decodes a report's stack with them ("Crash reporting" in `modules/AGENTS.md`). The Android build also uploads native symbols to Crashlytics. `bundle exec fastlane android install_bundle` then installs that AAB on the connected device through `bundletool` (`brew install bundletool`), split the way Google Play splits it.
- `<platform> release` builds and uploads; `bundle exec fastlane release notes:<file>` builds all three, then uploads to App Store Connect (not submitted for review), to Google Play as a draft on `track:` (default `production`), and creates a draft GitHub release `v<version>` at HEAD with the APKs, `latest.json` and a zip of the source maps. Release lanes need a clean git tree. Notes come from the release-notes skill: `bundle exec fastlane notes` (after `bump`) runs it through `claude -p` with read-only git/gh tools and saves `build/release/v<version>/release-notes.md`, which the release lanes use when no `notes:` is given, so review and edit it first. It refuses a version that's already tagged. Without the `claude` CLI (or logged out, or with `claude:false`) it writes a draft with the commits since the last tag and `TODO(release-notes)` placeholders, and the release lanes won't upload notes that still have one. A release lane run in a terminal with no notes file writes them first and asks before building.
- The build lanes need the repo-root `.env` with the mock login (`DUMMY_USERNAME`, `DUMMY_PASSWORD`; `babel/inline-env.js` inlines it), and fail before building without it; a worktree has none, so copy it from the main checkout. After building they check that each JS bundle has the mock login and no other `.env` value.
- Secrets go in `fastlane/.env` (git-ignored; fastlane loads it); the `ENV` reads in `fastlane/Fastfile` are the keys it takes. Without the App Store Connect key fastlane asks for an Apple ID. Android signing reads `android/local.properties` (copy its `.example`) and `android/app/release.keystore`.
- TestFlight's What to Test uses the same notes as the store: once App Store Connect has processed an upload, `bundle exec fastlane <ios|mac> testflight_notes` sets it for this version's build (`build:` for another one) from the iOS or Mac section, or from `what_to_test:<text>` (both languages) for a build between releases, which has no notes yet. It uploads nothing and notifies no one; the release lanes print the command when they finish.
- External testers get a build only after Beta App Review: `bundle exec fastlane <ios|mac> beta_review` (same `build:`, `notes:` and `what_to_test:` options) sets What to Test, submits the processed build for review, and adds it to the external TestFlight groups named by `groups:<name,...>` or `TESTFLIGHT_EXTERNAL_GROUPS` (comma-separated) in `fastlane/.env`. Testers are notified when Apple approves it. In a terminal it says which build and groups and asks first. It's separate from the release lanes because a build can be submitted only after App Store Connect has processed it, and a build uploaded by hand (`fastlane run upload_to_testflight`) works too. It never submits for App Store review.
- Don't upload, submit or publish anything unless asked; `build` lanes are safe to run.

## The Electron app (Windows and Linux)

- Best effort: a mobile release never waits on it. It's released with mobile, on the same GitHub release, with the same version and build number (`pnpm bump` covers it: `electron/buildInfo.ts` reads `package.json` and the Xcode project). No macOS build: the Mac has the Catalyst app.
- `pnpm electron:package` (`electron/package.ts`) builds the unsigned installers and their update files (`latest*.yml`, `.blockmap`) on a Mac, Windows or Linux. The export needs the repo-root `.env` (the mock login) as the mobile builds do. The lanes below take installers built either way.
- Released by hand with fastlane, as the native apps are, never from CI: its `Electron / Installers` job only checks that packaging still works, and its artifacts are never released. In order, after `pnpm bump`, on the release commit:
  1. `bundle exec fastlane electron build`: the installers, `latest*.yml` and `.blockmap`s for Windows and Linux into `build/release/v<version>/electron/`. It packages them on this Mac, or copies them from folders built elsewhere with `from:/path/to/win,/path/to/linux` (`platforms:win` or `platforms:linux` for one). It refuses update files for another version, an installer an update file names that's missing or has another SHA-512, and installers whose names carry another version.
  2. `bundle exec fastlane electron sign`: runs `scripts/release/sign-electron-update.mjs` on that folder with the key read from 1Password (`op read` at `LEARNX_UPDATE_SIGNING_KEY_REF`, the key's `op://` reference in `fastlane/.env`; or `key:` / `LEARNX_UPDATE_SIGNING_KEY` for a file), which writes a `.sig` next to each `latest*.yml`.
  3. `bundle exec fastlane electron release` (build, sign and upload in one) adds everything in that folder, the `.sig` files included, to the draft `v<version>` that `fastlane release` or `github_release` made, and refuses a published one. Or `bundle exec fastlane release electron:true` (with `from:` as above) builds and signs it with the other platforms and puts it on the draft it makes. Publish the release with the mobile files.

  Skipping a step:
  - A build from another commit carries another version; the lanes and the signing script refuse it.
  - Without step 2, or without uploading the `.sig` files, installs refuse the update and stay on their version until a signed one is out. New downloads still work.
  - Without the `latest*.yml` files, the mirror offers no Windows or Linux update.

  Upload before publishing: the TUNA mirror copies the latest published release on its schedule, and a file added later reaches users only at its next copy.

- The app downloads nothing whose update file has no valid signature by the Electron update key ("Packaging and updates" in `electron/AGENTS.md`), so an unsigned release offers Windows and Linux users no update. Sign after any change to a `latest*.yml`. The signing script refuses an update file for another version and a placeholder key.
- Install instructions (Windows SmartScreen, the AppImage and the .deb) live in the README, not in the release notes.
- Try an update before releasing, without publishing: on a Windows PC build two test versions with `pnpm electron:package --win --update-url http://localhost:8299/` (`--version` sets each one's version), and serve a folder with `node electron/updateServer.ts <folder>`, which stands in for the mirror's `LatestRelease/`. Install the older one with its installer, `latest.yml` and `.blockmap` in the folder, then copy the newer one's in with `latest.yml.sig` signed as above (with `--version` set to the newer one's): the app downloads it and offers Restart in Settings.

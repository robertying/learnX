# Releasing learnX

- [fastlane](https://docs.fastlane.tools) (`fastlane/Fastfile`) builds and uploads releases on a Mac. It and CocoaPods are in the `Gemfile`: run `bundle install` once (the Ruby in `.ruby-version`, e.g. Homebrew's), then `pnpm install` and `cd ios && bundle exec pod install` (the locked CocoaPods and `Podfile.lock`; not `pnpm pod`, which also updates pods) before building.
- A feature release gets What's New highlights before it's built: an entry for its version at the top of `releases` in `src/helpers/whatsNew.ts` (up to `maxHighlights` (5) rows on each platform (`ios`, `mac`, `android`, `electron`), strings in `en.ts` / `zh.ts`, `minNative` on rows that need the new native code, `platforms` on rows that only some platforms have, such as widgets, which the Mac lacks). A bug-fix release gets none: it shows no What's New, and its notes are in Settings › Changelog.
- `pnpm bump major|minor|patch` or `pnpm bump x.y.z` (`bundle exec fastlane bump version:x.y.z`) sets the version in `package.json`, the Xcode project and `android/app/build.gradle`. The build number goes to the next multiple of 10 (18.0.3 is 4530), or up by 1 for a rebuild of the same version (`pnpm bump build`, or `pnpm bump` alone); the Android versionCode is 9200000 + the build number.
- If the release changes native code since the last one, also set the over-the-air runtime version in `app.json` to the new version and record it in `ota-fingerprint.json` (CI's "Runtime version" check says when, and prints the values; "Over-the-air updates" in `AGENTS.md`). A JS-only release keeps it. The build lanes refuse to build with the placeholder update URL in `app.json`.
- `bundle exec fastlane <ios|mac|android> build` builds into `build/release/v<version>/` without uploading anything: the .ipa, the Mac Catalyst .pkg, the AAB (the `googlePlay` flavor), the APKs (the `github` flavor, which update themselves) renamed `learnX-<abi>-v<version>.apk` with `latest.json` (each APK's size and SHA-256, what the in-app updater reads from the TUNA mirror and checks the download against; "Updating the Android app" in `modules/AGENTS.md`), and the JS source map of each build in `sourcemaps/`. Crashlytics doesn't symbolicate JS, so keep these maps: `bundle exec fastlane symbolicate` decodes a report's stack with them ("Crash reporting" in `modules/AGENTS.md`). The Android build also uploads native symbols to Crashlytics. `bundle exec fastlane android install_bundle` then installs that AAB on the connected device through `bundletool` (`brew install bundletool`), split the way Google Play splits it.
- `<platform> release` builds and uploads; `bundle exec fastlane release notes:<file>` builds all three, then uploads to App Store Connect (not submitted for review), to Google Play as a draft on `track:` (default `production`), and creates a draft GitHub release `v<version>` at HEAD with the APKs, `latest.json` and a zip of the source maps. Release lanes need a clean git tree. Notes come from the release-notes skill: `bundle exec fastlane notes` (after `bump`) runs it through `claude -p` with read-only git/gh tools and saves `build/release/v<version>/release-notes.md`, which the release lanes use when no `notes:` is given, so review and edit it first. It refuses a version that's already tagged. Without the `claude` CLI (or logged out, or with `claude:false`) it writes a draft with the commits since the last tag and `TODO(release-notes)` placeholders, and the release lanes won't upload notes that still have one. A release lane run in a terminal with no notes file writes them first and asks before building.
- The build lanes need the repo-root `.env` with the mock login (`DUMMY_USERNAME`, `DUMMY_PASSWORD`; `babel/inline-env.js` inlines it), and fail before building without it; a worktree has none, so copy it from the main checkout. After building they check that each JS bundle has the mock login and no other `.env` value.
- Secrets go in `fastlane/.env` (git-ignored; fastlane loads it): `APP_STORE_CONNECT_API_KEY_KEY_ID`, `APP_STORE_CONNECT_API_KEY_ISSUER_ID`, `APP_STORE_CONNECT_API_KEY_KEY_FILEPATH` (.p8) for App Store Connect and Xcode signing (without them fastlane asks for an Apple ID), `GOOGLE_PLAY_CONSOLE_JSON_KEY` (path to the Play service account JSON; `SUPPLY_JSON_KEY` works too), optionally `GITHUB_TOKEN` (otherwise `gh auth token`), and `LEARNX_UPDATE_SIGNING_KEY_REF` (the Electron update key's `op://` reference, for `electron sign`). Android signing reads `LEARNX_RELEASE_*` from `android/local.properties` (copy `android/local.properties.example`) and `android/app/release.keystore`.
- TestFlight's What to Test uses the same notes as the store: once App Store Connect has processed an upload, `bundle exec fastlane <ios|mac> testflight_notes` sets it for this version's build (`build:` for another one) from the iOS or Mac section. It uploads nothing and notifies no one; the release lanes print the command when they finish.
- Don't upload, submit or publish anything unless asked; `build` lanes are safe to run.

## The Electron app (Windows and Linux)

- Best effort: a mobile release never waits on it. It's released with mobile, on the same GitHub release, with the same version and build number (`pnpm bump` covers it: `electron/buildInfo.cjs` reads `package.json` and the Xcode project). No macOS build: the Mac has the Catalyst app.
- `pnpm electron:package` exports the web build and packages it with electron-builder (`electron/package.mjs`, `electron/packageConfig.cjs`) into `build/electron/dist/`: `learnX-Setup-<version>.exe` (one NSIS installer for x64 and arm64) with `latest.yml` and its `.blockmap`, and `learnX-<version>-<arch>.AppImage` / `.deb` (x64 and arm64) with `latest-linux.yml` and `latest-linux-arm64.yml`. `--win` or `--linux` builds one platform, `--dir` only the unpacked apps. The export needs the repo-root `.env` (the mock login) as the mobile builds do. Builds are unsigned. On an Apple silicon Mac the installers need Rosetta (electron-builder's macOS `makensis` and AppImage tools are Intel-only; without it they fail with spawn error -86), so without it build them on a Windows PC (`pnpm electron:package --win`, Windows only) and on Linux (`--linux`); on the Mac use `--dir`. Where release installers get built (Rosetta on the Mac, or the Windows PC and Linux) is still to be decided; the lanes below take either.
- Released by hand with fastlane, as the native apps are, never from CI: its Package jobs only check that packaging still works, and their artifacts are never released. The `electron` lanes are written but untested: check each step's output the first time. In order, after `pnpm bump`, on the release commit:
  1. `bundle exec fastlane electron build`: the installers, `latest*.yml` and `.blockmap`s for Windows and Linux into `build/release/v<version>/electron/`. It packages them on this Mac where it can (Rosetta), or copies them from folders built elsewhere with `from:/path/to/win,/path/to/linux` (`platforms:win` or `platforms:linux` for one). It refuses update files for another version, an installer an update file names that's missing or has another SHA-512, and installers whose names carry another version.
  2. `bundle exec fastlane electron sign`: runs `scripts/sign-electron-update.mjs` on that folder with the key read from 1Password (`op read` at `LEARNX_UPDATE_SIGNING_KEY_REF`, the key's `op://` reference in `fastlane/.env`; or `key:` / `LEARNX_UPDATE_SIGNING_KEY` for a file), which writes `latest.yml.sig`, `latest-linux.yml.sig` and `latest-linux-arm64.yml.sig`.
  3. `bundle exec fastlane electron release` (build, sign and upload in one) adds everything in that folder, the `.sig` files included, to the draft `v<version>` that `fastlane release` or `github_release` made, and refuses a published one. Or `bundle exec fastlane release electron:true` (with `from:` as above) builds and signs it with the other platforms and puts it on the draft it makes. Publish the release with the mobile files.

  Skipping a step:
  - A build from another commit carries another version; the lanes and the signing script refuse it.
  - Without step 2, or without uploading the `.sig` files, installs refuse the update and stay on their version until a signed one is out. New downloads still work.
  - Without the `latest*.yml` files, the mirror offers no Windows or Linux update.

  Upload before publishing: the TUNA mirror copies the latest published release on its schedule, and a file added later reaches users only at its next copy.

- The signature (`scripts/sign-electron-update.mjs`): each `latest*.yml` gets a detached Ed25519 signature by learnX's Electron update key, checked against the public key in `certs/electron-update.pem`. The script refuses an update file whose `version:` isn't `package.json`'s (`--version` names another, for test builds), and a placeholder key file (its first line says `PLACEHOLDER`), as `pnpm electron:package` does for anything but `--dir` and local test builds, so no installer that could never update is made. The app downloads nothing whose update file has no valid signature (`electron/updateSignature.cjs`), so an unsigned release offers Windows and Linux users no update, and a mirror that changes `latest.yml` can't make them install anything. Sign after any change to a `latest*.yml`.
- The update key (not the over-the-air key, which stays the update server's) is in place: its public half is `certs/electron-update.pem`, its private half in Rui's 1Password. Rotate it only if the private half leaks, with the command in `electron/AGENTS.md` (Signing updates): installs trust only the key they were built with, so the first release with a new one must be installed by hand.
- On the release: asset names have no spaces (GitHub turns them into dots, breaking the links in `latest.yml`); `packageConfig.cjs` names every file without them. Installed apps update from the TUNA mirror's copy of the latest release (`LatestRelease/`, as the Android APKs do), reading its `latest*.yml` files and their signatures: a release without them offers Windows and Linux users no update. They check about 10 seconds after launch and every 4 hours (half an hour after a failed check, as when the mirror has `latest.yml` but not yet the installer), download in the background, and install on quit or when the user restarts from Settings.
- Release notes: the GitHub text gets a short Windows and Linux part: Windows SmartScreen warns about the unsigned installer, so say to choose "More info", then "Run anyway" (Chinese: "更多信息", then "仍要运行"). On Linux: `chmod +x` the AppImage, or install the .deb with `sudo apt install ./learnX-<version>-amd64.deb` (a .deb says when an update is out, in Settings, and links to its .deb; it doesn't install it). On Ubuntu 24.04 and later, say to use the .deb: Ubuntu restricts the unprivileged user namespaces Electron's sandbox needs, so the AppImage may not start, and the .deb installs an AppArmor profile that allows it (Chinese: Ubuntu 24.04 及以上版本请安装 .deb 包).
- Try an update before releasing, without publishing: on the Windows PC build two test versions with `pnpm electron:package --win --update-url http://localhost:8299/` (`--version` sets each one's version), and serve a folder with `node electron/updateServer.mjs <folder>`, which stands in for the mirror's `LatestRelease/`. Install the older one with its installer, `latest.yml` and `.blockmap` in the folder, then copy the newer one's in with `latest.yml.sig` signed as above (with `--version` set to the newer one's): the app downloads it and offers Restart in Settings.

# Upgrading learnX's dependencies

learnX declares versions in many places besides `package.json`. An upgrade covers all of them: the inventory below lists each place, how to find its latest version and how to move it.

## Rules

- Go to the **latest** release of everything, including majors, Node and GitHub Actions. Do the code migration a major needs in the same change. When the latest can't work yet (an Expo SDK that doesn't support it, a peer that caps it, a regression), take the newest version that does and say why in the pull request.
- Ask before adding a **new** dependency, including a new peer dependency a bump starts asking for. Removing one that nothing uses any more is fine; say so in the pull request.
- `package.json` has one `dependencies` list (no `devDependencies`), with exact versions (no `^` or `~`).
- Upgrades are done by hand with this skill, which covers every place a version is declared.
- Minimum OS versions are a support decision, not a dependency: leave the iOS deployment target (`ios/Podfile`, `ios/learnX.xcodeproj`, the module podspecs; Mac Catalyst follows it) and Android's `minSdkVersion` alone unless asked, unless a new React Native or Expo SDK requires a higher one (then raise every place together and update the minimum versions in `README.md` and `CONTRIBUTING.md`).
- Likewise leave the Java toolchain (`javaVersion`, `java-version` in CI) where it is unless the React Native template moves it.
- learnX's own Swift is in Swift 6 language mode (`SWIFT_VERSION = 6.0` on every target in `ios/learnX.xcodeproj`, `s.swift_version` in the module podspecs). Keep it there and fix new strict-concurrency errors a bump brings in code, not by lowering the mode. Pods from `node_modules` keep their own setting: the Podfile's `post_install` puts pods whose podspec names no Swift version in Swift 5 mode, since CocoaPods would otherwise give them the app's.

## Order

Upgrade in this order, since each step decides what the next can take. Separate pull requests per group (JS packages, Expo SDK and React Native, iOS tooling, Android build, CI and Node) are easier to review and bisect than one.

1. **Node and pnpm** first, so installs run on the new ones.
2. **Expo SDK and React Native.** Move `expo` to the latest SDK, then run `npx expo install --check` (and `--fix`) to put every `expo-*`, `@expo/ui` and `babel-preset-expo` on that SDK's versions. React Native goes to the newest release that SDK supports, and moves together with `@react-native/*` (`jest-preset`, `metro-config`, `typescript-config`), `@react-native-community/cli*` (the version the React Native template uses), `react` (the version React Native requires, also set as `settings.react.version` in `.oxlintrc.json`, which a tooling test checks) and `@types/react`. For a new React Native release, go through the [Upgrade Helper](https://react-native-community.github.io/upgrade-helper/) diff and carry the template changes into `android/` and `ios/` (Gradle files, `MainApplication`, `AppDelegate`, `Podfile`), keeping learnX's own changes. Read the Expo SDK and React Native changelogs for breaking changes.
3. **Packages tied to React Native or each other**: `react-native-reanimated` with the `react-native-worklets` version its compatibility table lists; `react-native-screens`, `react-native-gesture-handler`, `react-native-safe-area-context`, `@react-navigation/*` and `react-native-bottom-tabs` / `@bottom-tabs/react-navigation`; `typescript` with `oxlint-tsgolint` (its version tracks TypeScript's); `jest` with `@types/jest`, `@testing-library/react-native` and `test-renderer`; `@tanstack/*` together.
4. **Every other npm package**: `pnpm outdated`, then `pnpm add <pkg>@<version>` per package (or edit `package.json` and `pnpm install`). Nothing may stay behind without a reason. pnpm waits a day before installing a fresh release (`minimumReleaseAge`); that's the latest you can take.
5. **Transitive packages**: `pnpm update` then `pnpm dedupe` to refresh the lockfile within each package's ranges. A patched transitive package (`whatwg-fetch`) follows whatever React Native depends on.
6. **Patches** for every patched package whose version changed (below).
7. **iOS**: Ruby, then `bundle update --all` and `bundle update --bundler` (raise the `~>` floors in the `Gemfile` to the new minor versions first), then `pnpm pod` (`pod install` and `pod update`, which also moves the unversioned Firebase pods). Read the `Podfile.lock` diff.
8. **Android**: the Android Gradle Plugin and Gradle together, then Kotlin and KSP, the SDK versions, the other plugins and libraries. Update the wrapper with `cd android && ./gradlew wrapper --gradle-version <version> --distribution-type bin`, run it a second time so the new Gradle rewrites the scripts and jar, and commit all four wrapper files. A `targetSdkVersion` bump changes app behavior: read Android's behavior changes for that API level. When the Android Gradle Plugin moves, check whether the opt-outs in `android/gradle.properties` (`android.builtInKotlin`, `android.newDsl`) are still needed by React Native and Expo.
9. **CI**: Actions, runners and tools in the workflows. Keep the change detection regexes (`scripts/changed-files.sh` callers) in step with any file you add or rename.
10. **Docs**: `CONTRIBUTING.md`'s tools table and SDK steps, `patches/README.md`, and any `AGENTS.md` that names a version or a version-specific behavior (e.g. React Compiler 1.0, Testing Library v14).

## Patches

Each patch is pinned to the exact version it patches (`patches/<name>@<version>.patch`, a scoped name's `/` as `__`), so bumping a patched package fails `pnpm install` until its patch moves too.

1. Check whether the new release fixes the issue upstream (the "Drop when" column in `patches/README.md`, the package's changelog and source). If it does, delete the patch file, its `patchedDependencies` entry and its README row.
2. Otherwise, bump the version and remove the old `patchedDependencies` entry, then `pnpm install`.
3. `pnpm patch <pkg>@<new version>` and apply the old patch in the folder it prints: `git apply --reject <repo>/patches/<old>.patch` (the paths are relative to the package folder). Resolve any `.rej` hunks by hand against the new code, and drop hunks that are now upstream.
4. `pnpm patch-commit <folder>` writes `patches/<name>@<new version>.patch` and the new `patchedDependencies` entry. Delete the old patch file, and update the package's row in `patches/README.md` if what the patch does changed.
5. `scripts/check-patches.sh` must pass. In a checkout whose `node_modules` came from somewhere else, `pnpm install --force` reapplies every patch; run `bundle exec pod install` in `ios/` after that, since the reinstall wipes the `sqlite3.h` that expo-sqlite's pod copies in.

## Verify

Everything here must pass before the pull request is merged:

- `pnpm install --frozen-lockfile` is clean: no skipped install scripts (add a needed one to `allowBuilds` only after asking, like a new dependency) and no new peer dependency warnings.
- `scripts/check-patches.sh`
- `pnpm format`, then `pnpm typecheck`, `pnpm lint --deny-warnings`, `pnpm format --check` and `pnpm test`. New lint rules or type errors from a bump are fixed in code, not turned off.
- JS bundles for both platforms (with a `.env` copied from `.env.example`): `npx react-native bundle --platform ios --dev false --entry-file index.js --bundle-output /tmp/learnx-ios.js` and the same with `--platform android`.
- iOS (on a Mac): `cd ios && bundle exec pod install`, `scripts/test-ios.sh <simulator udid>`, then build and launch the app on an iOS simulator and as the Mac Catalyst app (`pnpm ios`, or Xcode with "My Mac (Mac Catalyst)"); the widget and share extensions build with it.
- Android: `scripts/test-android.sh`, `cd android && ./gradlew :app:assembleDebug :app:assembleRelease` (the release build runs R8), then install and launch on an emulator.
- In the running app, log in with the mock account (`src/data/AGENTS.md`) and go through the areas the upgraded packages drive: every tab and its lists, a notice and an assignment detail (web view), a PDF file, the course timetable, search, swipe actions, Settings, and the widgets. The Maestro flows (`pnpm e2e:ios`, `pnpm e2e:android`) cover the main paths.
- CI is green.

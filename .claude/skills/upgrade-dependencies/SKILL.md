# Upgrading learnX's dependencies

learnX declares versions in many places besides `package.json`. An upgrade covers all of them: the inventory below lists each place, how to find its latest version and how to move it.

## Rules

- Go to the **latest** release of everything, including majors, Node and GitHub Actions. Do the code migration a major needs in the same change. When the latest can't work yet (an Expo SDK that doesn't support it, a peer that caps it, a regression), take the newest version that does and say why in the pull request.
- Ask before adding a **new** dependency, including a new peer dependency a bump starts asking for. Removing one that nothing uses any more is fine; say so in the pull request.
- The root `package.json` has one `dependencies` list (no `devDependencies`), with exact versions (no `^` or `~`). The Electron app's workspace package, `electron/package.json`, keeps exact versions too.
- Upgrades are done by hand with this skill, which covers every place a version is declared.
- Minimum OS versions are a support decision, not a dependency: leave the iOS deployment target (`DEPLOYMENT_TARGET` in `modules/learnx_module.rb`, which the Podfile and the module podspecs read, and `ios/learnX.xcodeproj`; Mac Catalyst follows it) and Android's `minSdkVersion` alone unless asked, unless a new React Native or Expo SDK requires a higher one (then raise every place together and update the minimum versions in `README.md`).
- Likewise leave the Java toolchain (`javaVersion`, `java-version` in CI, `toolchainVersion` in `android/gradle/gradle-daemon-jvm.properties`) where it is unless the React Native template moves it; when it moves, regenerate that file with `./gradlew updateDaemonJvm --jvm-version <version>` in `android/`.
- learnX's own Swift is in Swift 6 language mode (`SWIFT_VERSION = 6.0` on every target in `ios/learnX.xcodeproj`, `s.swift_version` in `modules/learnx_module.rb`, which every module podspec uses). Keep it there and fix new strict-concurrency errors a bump brings in code, not by lowering the mode. Pods from `node_modules` keep their own setting: the Podfile's `post_install` puts pods whose podspec names no Swift version in Swift 5 mode, since CocoaPods would otherwise give them the app's.

## Order

Upgrade in this order, since each step decides what the next can take. Separate pull requests per group (JS packages, Expo SDK and React Native, iOS tooling, Android build, CI and Node) are easier to review and bisect than one.

1. **Node and pnpm** first, so installs run on the new ones.
2. **Expo SDK and React Native.** Move `expo` to the latest SDK, then run `npx expo install --check` (and `--fix`) to put every `expo-*`, `@expo/ui` and `babel-preset-expo` on that SDK's versions. React Native goes to the newest release that SDK supports, and moves together with `@react-native/*` (`jest-preset`, `metro-config`, `typescript-config`), `@react-native-community/cli*` (the version the React Native template uses), `react` (the version React Native requires, also set as `settings.react.version` in `.oxlintrc.json`, which a tooling test checks) and `@types/react`. For a new React Native release, go through the [Upgrade Helper](https://react-native-community.github.io/upgrade-helper/) diff and carry the template changes into `android/` and `ios/` (Gradle files, `MainApplication`, `AppDelegate`, `Podfile`), keeping learnX's own changes. Read the Expo SDK and React Native changelogs for breaking changes.
3. **Packages tied to React Native or each other**: `react-native-reanimated` with the `react-native-worklets` version its compatibility table lists; `react-native-screens`, `react-native-gesture-handler`, `react-native-safe-area-context`, `@react-navigation/*` and `react-native-bottom-tabs` / `@bottom-tabs/react-navigation`; `typescript` with `oxlint-tsgolint` (its version tracks TypeScript's); `jest` with `@types/jest`, `@testing-library/react-native` and `test-renderer`; `@tanstack/*` together.
4. **Every other npm package**: `pnpm outdated` and `pnpm --filter learnx-electron outdated`, then `pnpm add <pkg>@<version>` per package (`pnpm --filter learnx-electron add` for the Electron app's) (or edit `package.json` and `pnpm install`). Nothing may stay behind without a reason. pnpm waits a day before installing a fresh release (`minimumReleaseAge`); that's the latest you can take.
5. **Transitive packages**: `pnpm update` then `pnpm dedupe` to refresh the lockfile within each package's ranges. A patched transitive package (`whatwg-fetch`) follows whatever React Native depends on.
6. **Patches** for every patched package whose version changed (below).
7. **iOS**: Ruby, then `bundle update --all` and `bundle update --bundler` (raise the `~>` floors in the `Gemfile` to the new minor versions first), then `pnpm pod:update` (`pod install` and `pod update`). Read the `Podfile.lock` diff. Then Firebase: raise `minimumVersion` of the `firebase-ios-sdk` package in `ios/learnX.xcodeproj` to the latest release (for a new major version, also its `kind`), delete `Package.resolved` and run `xcodebuild -resolvePackageDependencies -workspace ios/learnX.xcworkspace -scheme learnX`, which writes it again with the newest versions in range. Read its diff.
8. **Android**: the Android Gradle Plugin and Gradle together, then Kotlin and KSP, the SDK versions, the other plugins and libraries. Update the wrapper with `cd android && ./gradlew wrapper --gradle-version <version> --distribution-type bin`, run it a second time so the new Gradle rewrites the scripts and jar, and commit all four wrapper files. A `targetSdkVersion` bump changes app behavior: read Android's behavior changes for that API level. When the Android Gradle Plugin moves, check whether the opt-outs in `android/gradle.properties` (`android.builtInKotlin`, `android.newDsl`) are still needed by React Native and Expo.
9. **CI**: Actions, runners and tools in the workflows. Maestro moves together with the patched build (below). Keep the change detection regexes (`scripts/ci/changed-files.sh` callers) in step with any file you add or rename. A bump of only the Electron app's packages (Electron, electron-builder, electron-updater, Playwright) still changes `pnpm-lock.yaml`, so the required Android job does its full build: that's accepted, since such bumps are rare.
10. **Docs**: `patches/README.md`, and any doc that names a version-specific behavior (`git grep` for the old major).

## Patches

Each patch is pinned to the exact version it patches (`patches/<name>@<version>.patch`, a scoped name's `/` as `__`), so bumping a patched package fails `pnpm install` until its patch moves too.

1. Check whether the new release fixes the issue upstream (the "Drop when" column in `patches/README.md`, the package's changelog and source). If it does, delete the patch file, its `patchedDependencies` entry and its README row.
2. Otherwise, bump the version and remove the old `patchedDependencies` entry, then `pnpm install`.
3. `pnpm patch <pkg>@<new version>` and apply the old patch in the folder it prints: `git apply --reject <repo>/patches/<old>.patch` (the paths are relative to the package folder). Resolve any `.rej` hunks by hand against the new code, and drop hunks that are now upstream.
4. `pnpm patch-commit <folder>` writes `patches/<name>@<new version>.patch` and the new `patchedDependencies` entry. Delete the old patch file, and update the package's row in `patches/README.md` if what the patch does changed.
5. `scripts/checks/check-patches.sh` must pass. In a checkout whose `node_modules` came from somewhere else, `pnpm install --force` reapplies every patch; run `bundle exec pod install` in `ios/` after that, since the reinstall wipes the `sqlite3.h` that expo-sqlite's pod copies in.

## Maestro

The E2E flows run on Maestro built from source with learnX's patches (`scripts/e2e/maestro/`, see its `README.md`); CI's Android E2E job runs the released Maestro named by `MAESTRO_VERSION`. Both stay on the same Maestro release.

1. Find the latest release: `gh api repos/mobile-dev-inc/Maestro/releases/latest --jq .tag_name` (tags look like `v2.12.1`). Compare it with `MAESTRO_VERSION` in `.github/workflows/android.yml` and with the release `base` in `scripts/e2e/maestro/build.sh` builds on (`git describe --tags <base>` in the Maestro checkout).
2. Check which patches the release includes upstream: the upstream issue or pull request each one names in `scripts/e2e/maestro/README.md`, and the release notes. A patch that is upstream is dropped: remove it from `build.sh`'s `git am` list and from `README.md`, and delete the file (`scripts/__tests__/maestro.test.ts` checks the three agree). Search the repo for its name (`git grep <patch file>`, and for what it adds, such as `setFoldPosture`) and update what says the patched build is needed for it (`.maestro/AGENTS.md`, flow and script comments).
3. Make a checkout with the current patches: `MAESTRO_SOURCE=<folder>/Maestro scripts/e2e/maestro/build.sh <install folder>` clones the base there, applies them on the branch `learnx-patched` and keeps it. Move it onto the release in the checkout: `git fetch --unshallow --tags https://github.com/mobile-dev-inc/Maestro.git`, then `git rebase --onto <tag> <old base> learnx-patched`, resolving conflicts against the new code and dropping commits of patches that are now upstream.
4. Write the patches back from the rebased commits, one file per patch in `build.sh`'s order: `git format-patch --stdout <from>..<to> > <repo>/scripts/e2e/maestro/<name>.patch`, where `<from>` is the tag for the first patch and the previous patch's last commit after that, and `<to>` is the patch's own last commit (`maestro-fold-posture.patch` holds several commits). Set `base` in `build.sh` to the release's commit (`git rev-parse <tag>^{commit}`).
5. Rebuild from the repo with `scripts/e2e/maestro/build.sh <install folder>` (no `MAESTRO_SOURCE`), so the build starts from the new `base` and applies the written patches. Delete the checkout afterwards. If the build needs a new workaround (the grpc pin, the driver's deployment target), change `build.sh` and say why in its comments; drop one the new release makes unneeded, such as the grpc pin once Maestro's own grpc is 1.76 or newer.
6. Set `MAESTRO_VERSION` in `.github/workflows/android.yml` to the same release.
7. With the new build first on `PATH`, run the flows: `pnpm e2e:ios` and `pnpm e2e:android`, plus the profiles only the patched build covers: `pnpm e2e:devices ipad-windowed duo-folded duo-half-open duo-open` (`scripts/e2e/e2e-devices.sh` lists the simulators each needs).

## Verify

Everything here must pass before the pull request is merged:

- `pnpm install --frozen-lockfile` is clean: no skipped install scripts (add a needed one to `allowBuilds` only after asking, like a new dependency) and no new peer dependency warnings.
- `scripts/checks/check-patches.sh`
- `pnpm format`, then `pnpm check`. New lint rules or type errors from a bump are fixed in code, not turned off. A bump that changes native code moves the native fingerprint: set the runtime version or update `ota-fingerprint.json` as the check says ("Over-the-air updates" in `AGENTS.md`), with CI's values, which come from a clean checkout.
- `scripts/checks/check-release-bundle.sh` (with the mock login in `.env`) builds both platforms' release JS bundles.
- iOS (on a Mac): `cd ios && bundle exec pod install`, `scripts/checks/test-ios.sh <simulator udid>`, then build and launch the app on an iOS simulator and as the Mac Catalyst app (`pnpm ios`, or Xcode with "My Mac (Mac Catalyst)"); the widget and share extensions build with it.
- Android: `scripts/checks/test-android.sh`, `cd android && ./gradlew :app:assembleGithubDebug :app:assembleGithubRelease :app:bundleGooglePlayRelease` (the release builds run R8), then install and launch on an emulator.
- The Electron app (Electron, electron-builder, electron-updater, Playwright): `pnpm e2e:electron`, and `pnpm electron:package --dir`. When Electron, electron-builder, electron-updater or a patch of theirs changes, also run a real update: the Electron workflow by hand (`Update E2E tests`), or `pnpm e2e:electron:update` on Windows or Linux. After an electron-builder upgrade, move `toolsets` in `electron/packageConfig.ts` to the newest AppImage runtime and NSIS bundle it knows (a test fails if a value isn't one of them), then start the x64 and arm64 AppImages on a stock Ubuntu (a virtual machine works), where a missing `libfuse2` or `libz.so` would stop them, and install the .deb there.
- In the running app, log in with the mock account (`src/data/AGENTS.md`) and go through the areas the upgraded packages drive: every tab and its lists, a notice and an assignment detail (web view), a PDF file, the course timetable, search, swipe actions, Settings, and the widgets. The Maestro flows (`pnpm e2e:ios`, `pnpm e2e:android`, run on the patched Maestro) cover the main paths.
- CI is green.

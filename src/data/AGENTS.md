# src/data

## Data

- Settings (`src/data/settings.ts`) and the user's own data (`src/data/userData.ts`: archives, hidden courses, course order, and the server actions not sent yet) are Zustand stores persisted to `expo-sqlite/kv-store`. Storage is synchronous, so the stores hold their saved state as soon as they are imported (also in the background task). Read them with `useSettings` / `useUserData` in components and `getSettings` / `getUserData` elsewhere; change them through the exported functions, not `setState` from screens.
- Every persisted store is listed in `accountStores` (`data/accountData`) with how it's emptied, and a test fails for one that isn't, so logging out or switching accounts never leaves one behind.
- When the persisted shape of a store changes, bump its `version` and add a `migrate`. Keep `merge` filling in defaults for keys added later.
- `src/data/legacy.ts` imports what 18.0.x saved in AsyncStorage (`persist:settings`, and the user data inside the slices of `persist:root`) once, before the UI shows, then deletes both keys. Don't remove it while users can still upgrade from 18.0.x.
- TODO: test the upgrade from 18.0.3 on Android. It has been run on the iOS simulator and Mac Catalyst: install 18.0.3, log in with the persistent mock account, change favorites, archives, hidden courses, course order, semester and settings, then install the current build over it. Check that all of it is kept, the AsyncStorage keys and `persist_auth` are removed, and the app stays logged in. Use signed debug builds: an unsigned iOS build loses the keychain login on relaunch, even in 18.0.3.
- Server data is in TanStack Query (client in `src/data/queryClient.ts`). Semesters, courses and the user are queries (`data/queries.ts`), and so are notices, assignments and files (`data/content.ts`, which also refreshes one course's items for CourseDetail). The lists are fetched course by course through one shared limiter (4 courses at a time, assignments first); a course that fails keeps its cached items, and a list fails only when every course does. thu-learn-lib (`@robertying/thu-learn-lib`, pinned to an exact version) makes per-item requests opt-in: an assignment's detail (description, attachments, submission, answer; two requests each) and a notice's attachment (one request) are only fetched for items that are new or whose list entry changed, and the others keep what the cache has. Refreshing one course (CourseDetail, or after a submission) fetches every item's detail again. An excellent homework's attachment is fetched when AssignmentDetail shows it (`useExcellentHomeworkDetail`). Courses are fetched with their time and location (`timeAndLocation: true`). Courses stay fresh for a day (pull to refresh on Courses refetches); the semester being shown is `currentSemester` in `data/userData`. Each response is saved to its own SQLite database (`queryCache`) by the per-query persister and loaded back into memory before the UI shows (`restoreQueryCache`), so lists show cached data before the login finishes and offline. Queries run only while logged in (`enabled: loggedIn`). Bump `QUERY_CACHE_VERSION` when a response's shape changes. Server times are Beijing time, and thu-learn-lib (6.0 and later) gives them as ISO 8601 strings with the offset (`2026-11-07T18:28:00+08:00`), so `dayjs()` reads the right moment in any time zone; `data/content.ts` compares them as moments (`sameServerTime` in `helpers/serverTime`). A file shared to learnX that is waiting to be attached to a submission lives in `data/pendingAssignment` (not persisted). A submission is sent the way the website's submit page sends it (`sendSubmission`, `submitAssignment`: thu-learn-lib's `getHomeworkSubmitRequest` builds the request and `checkHomeworkSubmitResponse` reads the answer, and axios sends it for the upload progress): the whole answer as HTML every time (`homeworkContentHtml`), since the server replaces the submitted one with it (an unedited answer goes back as the submitted HTML; removing the attachment keeps the text), and `fileupload` is the text `undefined` when no file is picked.
- Favorites are the website's (我的收藏): an item field `isFavorite`, which the notice and assignment lists carry, and which files get from thu-learn-lib's `getFileList(..., { favorites: true })` (6.1.0; the file list has no such field, so the library fetches the course's file favorites next to it; if that fails, the course keeps its cache). Archives and hidden courses stay on the phone, as the website has nothing like them.
- Everything that changes the account goes through one queue of server actions (`data/serverActions`, types and list changes in `data/pendingActions`): `favorite` (add or remove; both are safe to repeat) and `noticeRead` (loads the notice's page, which marks it read). An action is shown right away (`showFavorite`, `markNoticeRead`), saved in `userData.pendingActions` (one per item: the last wins) and sent at once if logged in; otherwise it's sent on login, when the app comes back to the foreground, at the start of `syncContent`, on logout (one quick try) and, for the notification's Favorite button with the app not running, after `ensureSession`. Waiting actions, and ones the server took after a fetch started, are laid over every response and over the cached lists, so a refresh never undoes them. A network error or failed login keeps the action without counting; an HTTP error (an unknown id answers 500) counts, and the third drops it. Debug builds keep favorite changes queued until "Allow Server Writes" is on. Favorites kept on the phone before this (user data version 1, or 18.0.x) are queued as adds once; nothing is removed on either side. To add a kind, add it to `ServerAction` and `actionChange` and give it a handler.
- Today's timetable (`data/schedule.ts`, logic in `helpers/schedule.ts`) comes from the registrar's calendar (`getCalendar`), which is fragile: it fails for long ranges and now and then for no clear reason, so it's asked for one week at a time (a query per week, one request at a time, retries on failure; thu-learn-lib gets the registrar's ticket itself), and a week that fails keeps what was last fetched for it. A week never fetched is worked out from each course's `timeAndLocation` (`星期一第2节(1-8周)，…`, or `Section 2 of Mon (Week 1-8 ), …` when the website is in English), the class period times and the term's first day (`semesterDatesQuery`), read with thu-learn-lib's `parseCourseMeeting`, `CLASS_PERIOD_TIMES` and `semesterWeek`, with a note that holidays and moved classes may be missing. The timetable follows Beijing days, also on a phone in another time zone: class times are Beijing times (`beijingTime`), Today and Up Next pick the classes of the current Beijing day (`beijingDate`, `useBeijingDay`), and times are shown in the phone's zone. Week 1 starts on the Monday of the term's first day, or the Monday after it when that day is a weekend (fall 2026 starts on Saturday Sep 12; week 1 is Sep 14–20). It doesn't depend on the calendar sync in Settings and isn't fetched by the background task. Calendar entries only name their course, so they're matched to courses by name.
- The background task (`helpers/background.ts`, `syncContent`) makes sure there's a session (`ensureSession`) and refetches the current semester's notices, assignments and files with the same per-course fetches, through the same limiter, as the screens' queries (`contentLists.<list>.fetchCourses` with a deadline, then `putCourses`), then compares them with what was cached using `diffContent` (`data/contentDiff.ts`): new items, newly graded assignments and moved deadlines. A list that wasn't cached before or failed to fetch reports no changes, so the first sync isn't all new.
- Login progress (`loggedIn`, `loggingIn`, the last error) is a Zustand store in `src/data/auth.ts` that isn't persisted; `src/data/login.ts` logs in, out and into the mock account. The credentials are in `src/data/credentials.ts`. There is no Redux.
- The saved data (server cache, user data, settings, drafts) belongs to one account, recorded as `dataOwner` (`src/data/dataOwner.ts`) apart from the credentials, which the ephemeral mock account and some logins don't keep. A successful login as anyone else drops all of it first (`clearAccountData` in `data/accountData`, the same steps as logout), so a new account never starts with the previous one's courses or timetable; logging in again as the same user (relaunch, resume, "Log in again", the persistent mock account) keeps it. Data saved before the owner was recorded counts as the saved login's.
- With a saved login the main UI stays up when a login fails: only the user's "Log in again" (`requestRelogin`) shows the login screen. A failed login is `failure: 'offline'` when its last attempt got no answer (thu-learn-lib's `NETWORK_ERROR` or `REQUEST_TIMEOUT`: `isNetworkError` in `helpers/parse`; such logins aren't retried right away), and `'rejected'` otherwise (`BAD_CREDENTIAL` for a wrong password, `ERROR_FETCH_FROM_ID` when the SSO server answered with something else). `components/SyncStatus` says so above each list, with how old the data is. `hooks/useReLogin` retries an offline login on a timer (30 s, 1 m, 2 m, then every 5 m) and on return to the app, but never retries a rejected one on its own, so a changed password isn't tried over and over. Coming back after 10 minutes or more checks the session with thu-learn-lib's `ensureSession` (`login({ resume: true })`: one request, and an SSO login only if the session expired) instead of a full login. Pull to refresh logs in when there's no session (`hooks/usePullToRefresh`). Work that needs a session but isn't a login (the background sync, a calendar sync, a file download again, a notification action with the app not running) calls `ensureSession` in `data/source`, never `loginWithFingerPrint`: it keeps a good session and logs in only when it has expired, and thu-learn-lib logs in again by itself when a request finds the session expired. When that login is turned down for a wrong password, the query and mutation caches' `onError` (`noteRequestError` in `data/auth`) ends the session as `'rejected'`, so the lists offer "Log in again". Logging out (`logout` in `data/login`) sends what's waiting first, then logs out on the server and clears the SSO cookie. A pull to refresh that fails shows a toast; refreshes the app starts itself don't. Coming back to the app refetches the mounted lists that are stale (after the relogin, if one was due). Opening a notice or downloading a course file marks it read in the cached list (`markNoticeRead`, `markFileSeen` in `data/content`; a notice is also marked read on the server through the `noticeRead` action, and a whole file download marks a file seen there, so files need no action), so the Unread filter and course counts change before the next refresh. The change is also applied to later responses in the same session, so a fetch already under way doesn't undo it.

## Mocks

### Mock login

The app can be used without a real Tsinghua account: enter `DUMMY_USERNAME` / `DUMMY_PASSWORD` from the repo-root `.env` on the login screen and it loads `src/data/mock.ts` instead of calling learn.tsinghua.edu.cn (see `src/screens/Login.tsx`). Use it for UI verification, screenshots and manual testing.

- These two values are not real credentials: reading them from `.env` and typing them into the UI is fine, even in tool calls. Do not print or commit any other value in `.env` (tokens, project IDs).
- In mock mode the app talks to an emulated server instead of learn.tsinghua.edu.cn: `src/data/mockSource.ts` answers every `dataSource` call (and assignment submission) with the mock data after a network-like delay, so refreshes, spinners and errors behave like a real account. File downloads go through the emulation too, then fetch the mock file's real URL. It also keeps the account's favorites (seeded from `mockFavorites`, in memory, so they start over when the JS reloads). Some features (e.g. course information sharing) still don't work offline.
- Debug builds show Settings › Network Emulation (also linked from the login screen when a mock account is saved) to change the latency, make requests and file downloads fail (offline, server error, 20 s timeout), reject logins, and log in again as the app does after 10 minutes in the background. The choices reset when the JS reloads.
- The default mock login is not persisted: every relaunch needs the login again, and its login results are ignored. To keep the mock data and session across relaunches, or to test failed logins and logging in again, log in with `DUMMY_PERSIST_USERNAME` / `DUMMY_PERSIST_PASSWORD` from `.env` instead (same data; relaunch logs in through the emulated server).

### Mock data

- `src/data/mock.ts` computes dates relative to now: keep new entries relative and free of sensitive info (emails, phone numbers, student IDs, URLs).
- It is meant to cover every UI state and to be good enough for store screenshots: real course names (with English names, which the emulated server returns when the app asks in English), made-up but plausible people's names (never real people), and notices and assignments with attachments, links, wide tables, an image and math, in every assignment state. Keep it that way when adding entries.
- Attachments and files download real sample files from `mock-files/` in this repo (via raw.githubusercontent.com on `main`, so a new sample only works once merged). `mock-files/generate.py` rebuilds them; add a sample there rather than linking to outside files.
- Assignment submission is disabled after the deadline, so keep some mock deadlines in the future.
- The mock courses have class times, and the mock semester began on the Monday eight weeks ago (`mockSemesterStart`), so it's always week 9; the emulated `getCalendar` works the week out from those times.

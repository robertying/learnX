# src/components

The app's component layer, the native controls it hosts, and the design rules screens follow.

## Components

- The app has its own small component layer in `src/components`; there is no UI kit. Space things with the scale in `constants/Spacing` and lay a group out with `gap` rather than a margin on each child, so neighbors' margins never add up. Colors come from `useTheme()` in `src/theme`.
- Text goes through `components/Text`, which draws each platform's own text styles (Dynamic Type on Apple platforms, the Material 3 type scale on Android, Fluent 2's ramp in the Electron app). Pick a style with `variant` instead of setting `fontSize`. It also follows a text size change made while the app runs, which a raw React Native `Text` won't. Android text uses the default typeface with no `fontFamily`: with a named family React Native draws only normal and bold, so medium and semibold would draw regular. Item titles are medium (500) on every platform, and unread items get a dot in the leading gutter (`CardGutter`), not a bolder title.
- Icons are named by meaning in `helpers/systemIcons`, which maps each to its SF Symbol, Material Symbol and Fluent System Icon. Add a new icon there with all three (and, for Android, its codepoint and, for `IconButton`, its drawable); tests check every platform has it.
- Toasts are shown with the module-level `toast()`, never through props or context.
- A screen or list with nothing to show, or that failed, uses `components/StatusView` (`Empty`, `NotFound` and the error screens are built on it).
- Notice, assignment and file cards are a `ContentCard`, which builds the spoken `accessibilityLabel` from the same values the row shows, including every state the row shows only visually. Give a new glyph or state to `ContentCard` as a flag, so the row and the label both get it. A card that isn't a `ContentCard` builds its own label the same way. Swipe, long-press and drag actions are also `accessibilityActions`.
- Card actions (`helpers/cardActions`): a swipe runs one action each way, as chosen in Settings › Swipe Actions, and looks like each platform's own (Mail on iOS, Gmail on Android). A long press shows every action in the platform's menu. With a keyboard (Mac, iPad), cards take focus as rows do in Mail.
- Native controls come from `@expo/ui`. A header's less used actions go in a menu (a native header menu on Apple platforms, `components/OverflowMenu` on Android). On Android every `Alert.alert` is a Material 3 dialog in the app's theme (`MaterialDialogModule` in `android/app`, with the `react-native` patch passing button styles), so give `style: 'destructive'` only to a button that deletes or discards at once. A form row that asks uses `FormChoiceButton`, whose dialog points at the row on iPad and Mac.
- Settings-style screens and the notice and assignment detail pages use `components/Form`: a SwiftUI `Form` on Apple platforms and the Material 3 grouped list on Android. Keep all of a form's look in `components/Form*.tsx`: screens only compose rows. Rows must be direct children of their section (fragments and conditionals are fine), since on Android the section rounds each row by its position, and a row component of your own must pass on the `position` prop it is given. The form scrolls by itself, so don't wrap it in a `ScrollView` or `KeyboardAvoidingView`; on Android it keeps clear of the keyboard itself (`components/KeyboardInsetView`).
- An `@expo/ui` view that exists on only one platform goes in a `.android.tsx` / `.ios.tsx` file, since `@expo/ui/jetpack-compose` and `@expo/ui/swift-ui` look up their native views when imported. Props both files share go in `X.shared.ts`: an `.android.tsx` can't value-import from `./X`, since Metro resolves that to itself. The Electron app's `.web.tsx` variants follow the same rule.
- Host native views in `components/ThemedHost` rather than `@expo/ui`'s `Host`, so Compose and SwiftUI views draw the theme's colors.

## Design rules

- Each platform looks like itself: native controls and idioms (Mail-style list rows, grouped forms, the system context menu on Apple platforms and Material menus on Android, Fluent controls and Windows 11 Settings' cards in the Electron app), not one shared design.
- Colors come from the platform: Apple's system colors on iOS, iPadOS and Mac, Material 3 color roles on Android, and Fluent's neutrals with the brand ramp in the Electron app. Never use a Material color on Apple platforms or an Apple system color on Android. The brand color (Tsinghua purple) is the tint on every platform.
- Icons are SF Symbols on Apple platforms, Material Symbols on Android and Fluent System Icons in the Electron app; an Android icon is never an iOS idiom (no share-sheet arrow box for Share).
- A meaning has one icon wherever it shows (a tab, a course card's counts, an empty list, a form row, a header button): reuse its `helpers/systemIcons` entry instead of picking a symbol for one screen.
- Deadlines follow one rule everywhere (cards, details, Today, widgets): `deadlineUrgency` in `helpers/assignments` (red under a day left, orange when due by the end of tomorrow). Passed deadlines and submitted assignments get no color, and the brand color never marks a deadline. The other status colors keep the same meanings: red for a favorite's heart, badges and destructive actions, orange for the important flag and a late submission, green for submitted. The brand color is for unread dots, grades, counts and form row icons, never a state. A detail page's status row shows its state by its icon, not by a color. Text in a status hue takes `theme.colors.onStatusContainer`, which keeps 4.5:1 contrast; `status` is for fills and glyphs.
- Permission prompts only follow a user action: a toggle turned on, an "Allow" row tapped. Syncs and refreshes the app starts itself check the permission without asking and skip quietly. When the system permission is off, the in-app toggles keep their state, and a row at the top of the screen asks again, or opens System Settings once the system won't ask.
- Haptics go through `playHaptic` from `services/haptics`, named by meaning, never `expo-haptics` directly. Play one only for something the user just did, once per action: a toast plays its type's haptic, so pass `{ haptic: false }` for a toast the user didn't cause or one confirming a gesture that already played its own. Native controls play their own or none, so don't add one. A swipe action plays the same tap whether a full swipe runs it or its revealed button is tapped.

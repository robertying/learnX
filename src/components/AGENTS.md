# src/components

The app's component layer, the native controls it hosts, and the design rules screens follow.

## Components

- The app has its own small component layer in `src/components`; there is no UI kit. Space things with the scale in `constants/Spacing` and lay a group out with `gap` rather than a margin on each child, so neighbors' margins never add up. Colors come from `useTheme()` in `src/theme` (`theme.colors`, `theme.dark`), with `onSurfaceHigh` and `onSurfaceMedium` as the title/body and caption text colors (iOS's `label` and `secondaryLabel`, Material 3's `onSurface` and `onSurfaceVariant`).
- Text uses `Text`, `Title`, `Headline`, `Paragraph` and `Caption` from `components/Text`, which draw the platform's own text styles: Apple's Dynamic Type styles on iOS, iPadOS and Mac (with `dynamicTypeRamp`, so each scales along its own curve) and the Material 3 type scale on Android. They add no margins of their own: space stacked text with `gap`. Pick a style with `variant` (`title`, `headline`, `body`, `subheadline`, `label`, `footnote`, `caption`) instead of setting `fontSize`; `textStyles` has the same styles for text `Text` doesn't draw, like a `TextInput`. Also there: `Divider`, `ProgressBar`, `Badge`, `IconButton` (a SwiftUI button with the icon's SF Symbol on iOS and Mac, a Compose icon button with its Material Symbol on Android; it takes a `helpers/systemIcons` name whose symbol has a drawable in `src/assets/icons/index.ts`, so add the drawable there for a new one), `SystemIcon` (any icon React Native draws itself, in rows, empty states, swipe actions and menus: a name from `helpers/systemIcons`, which maps it to an SF Symbol drawn natively by expo-symbols on iOS and Mac and to a Material Symbol from expo-symbols' font on Android; add a new icon there with both names and, for Android, its codepoint, which a test checks), `Touchable` (ripple on Android), `LoginFields` (the login's account and password: a SwiftUI `TextField` and `SecureField` with their `textContentType` in one host on iOS and Mac, which password AutoFill needs to offer saving them, and Compose outlined fields with an Autofill `contentType` on Android), `ContainedButton` and `Toast` (shown with the module-level `toast()`: a glass pill at the bottom of the window (above the iPhone tab bar and the keyboard) on iOS, iPadOS and Mac, drawn in a `FullWindowOverlay` so it shows over modals; the system `ToastAndroid` on Android).
- List cards hand `CardWrapper` a spoken `accessibilityLabel` built with `cardAccessibilityLabel` (`components/CardRow`): the title first, then whose and when, then every state the row shows only visually (unread dot or bold title, flag, paperclip, answer key), then a shortened preview. A new glyph or state goes in that label too. Swipe, long-press and drag actions are also `accessibilityActions` (course reorder offers Move Up / Move Down).
- Card actions (`helpers/cardActions`): a swipe runs one action each way, as chosen in Settings › Swipe Actions (`swipeActions` setting: right archives and left favorites by default; a course's Hide takes Archive's place). The swipe looks like each platform's own (`components/CardSwipeAction`): on iOS a Mail-style button the card rests open on, run by a tap or a full swipe; on Android a Gmail-style full-width background, run once the card slides off. A long press shows every action in a menu: the system context menu on iOS, iPadOS and Mac (right-click too), the Material dropdown (`components/CardMenu.android.tsx`) on Android. `TextField` gives its `label` to the input as its accessibility label.
- Native controls come from `@expo/ui`: `components/TextButton` (a borderless SwiftUI `Button` on iOS and Mac, the Material 3 text button on Android; `fill` for file names that shorten to one line), `components/Switch`, `components/SelectionMark` (SF Symbol circles on iOS and Mac, the Material checkbox on Android; display only), the Android card long-press menu (`components/CardMenu.android.tsx`, a Compose dropdown menu) and `components/DateRangePicker` (two SwiftUI date pickers in a sheet on iOS and Mac, Material's range picker dialog on Android). Search uses the native header search bar (`headerSearchBarOptions`), and choice sheets use `ActionSheetIOS` / `Alert`.
- Settings-style screens and the notice and assignment detail pages use `components/Form`: a SwiftUI `Form` (inset grouped sections, SF Symbols, native toggles and chevrons) on iOS, iPadOS and Mac, and the Material 3 grouped list (Compose `ListItem`s, Material Symbols) on Android. Build them from `FormSection` (title, footer caption) with `FormLink`, `FormButton` (`destructive`, `loading`, `disabled`, `selected` for a choice list), `FormToggle`, `FormNumberField`, `FormFile` (a file that opens on tap; `struck` when it is being replaced), `FormTextField` (full-width text, `multiline` grows from six lines; it keeps typed text itself and takes a new `value` only when it differs from what it reported, with `format` to clean what is typed, and a `label` for screen readers when the placeholder isn't a name) `FormProgress`, `FormText` (`detailTint` `accent` for a grade, `red` / `orange` for a deadline by `deadlineTone`), `FormTitle` (a detail page's title and subtitle, as in Calendar's event details); text and link rows take an `overline`, a short accent-colored line above the title (Material's overline, a caption on iOS and Mac) and `FormView` (a React Native view hosted in a row and sized by its content, such as the HTML body in `AutoHeightWebView`) rows, each with an `icon` (a `helpers/systemIcons` name) where it has one. A row component of your own (like AssignmentDetail's excellent homework row) must pass on the `position` prop it is given. Keep all of a form's look in `components/Form*.tsx`: screens only compose rows. Rows must be direct children of their section (fragments and conditionals are fine): on Android the section rounds each row by its position. The form scrolls by itself, so don't wrap it in a `ScrollView` or `KeyboardAvoidingView`.
- An `@expo/ui` view that exists on only one platform goes in a `.android.tsx` / `.ios.tsx` file, since `@expo/ui/jetpack-compose` and `@expo/ui/swift-ui` look up their native views when imported. Props both files share go in `X.shared.ts` (an `.android.tsx` can't value-import from `./X`: Metro resolves that to itself).
- Host native views in `components/ThemedHost` rather than `@expo/ui`'s `Host`: it seeds the palette from the theme's primary color, and on Android gives Compose the theme's whole Material palette (`useComposeColorOverrides`), so Compose and React Native views draw the same colors.

## Design rules

- Each platform looks like itself: native controls and idioms (Mail-style list rows, grouped forms, the system context menu on Apple platforms and Material menus on Android), not one shared design.
- Colors come from the platform: Apple's system colors (`PlatformColor`, `buildAppleColors` in `src/theme`) on iOS, iPadOS and Mac, Material 3 color roles on Android. Never use a Material color on Apple platforms or an Apple system color on Android. The brand color (Tsinghua purple) is the tint on both.
- Icons are SF Symbols on Apple platforms and Material Symbols on Android; an Android icon is never an iOS idiom (no share-sheet arrow box for Share).
- `helpers/systemIcons` names every icon in the app by meaning, so a meaning has one icon wherever it shows (a tab, a course card's counts, an empty list, a form row, a header or toolbar button): reuse its entry instead of picking a symbol for one screen. The tabs (`navigation/MainTab`) draw theirs filled on the iOS tab bar and as the outline in the Mac sidebar; Android's navigation bar loads them as vector drawables, `tab_<symbol>` and `tab_<symbol>_filled` for the selected tab, in `android/app/src/main/res/drawable` (paths from the Material Symbols font, 400 weight). Today's icon follows the time of day (`useDayPart`, `helpers/dayPart`). An empty list shows its section's icon and "No Notices", "No Files", … (`components/Empty`).
- Deadlines follow one rule everywhere (cards, details, Today, widgets): `deadlineUrgency` in `helpers/assignments` is `urgent` (red) under a day left, which `deadlineText` counts in hours, and `soon` (orange) when it's due by the end of tomorrow, which it counts as "1 day" (days are calendar days). Passed deadlines and submitted assignments get no color. Cards draw it as a pill, other places as the detail text in the same hue (`deadlineTone`); the brand color never marks a deadline. The other status colors follow the same meanings: red for a favorite's heart, badges and destructive actions, orange for the important flag and a late submission, green for submitted; the brand color is for unread dots, grades, counts and form row icons, never a state. A detail page's status row shows its state by its icon (done, submitted late, late submission open, missed), not by a color. Text in a status hue (a pill, a row's deadline) takes `theme.colors.onStatusContainer`, the hue's text shade, which keeps 4.5:1 contrast; `status` is for fills and glyphs.
- Permission prompts only follow a user action: a toggle turned on, an "Allow" row tapped. Syncs and refreshes the app starts itself check the permission without asking and skip quietly (`ask: !automatic` in `services/calendar/actions`). When the system permission is off, the in-app toggles keep their state, and a row at the top of the screen (Turn On Notifications in `screens/NotificationSettings`) asks again, or opens System Settings once the system won't ask.

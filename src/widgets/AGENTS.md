# src/widgets

- The home screen widgets (iOS and Android) are built with `expo-widgets`, with a layout per platform (`@expo/ui/swift-ui` on iOS, `@expo/ui/jetpack-compose` on Android, limited to what Glance supports). A function with the `'widget'` directive is turned into a string by the widgets Babel plugin and runs in the widget runtime: no hooks, imports or outside values, only its props and `environment`. Layouts also can't use what Babel compiles to helpers (array destructuring becomes `_slicedToArray`); a test checks their source. `src/widgets` is left out of the React Compiler.
- `services/surfaces` updates the widgets when their data changes (`src/services/AGENTS.md`). The widget, not the app, decides what's due or on now: iOS gets a timeline with an entry at each moment something changes, Android redraws on a timer, and each layout picks what to show by its own clock. So a widget stays right without the app running, up to the data the app last fetched.
- Taps open `learnx://` links (`getTargetUrl` in `helpers/openTarget.ts`), which `useLinkTaps` opens like any other tap from outside the app.
- Screen readers read each row as one element: combined on iOS, with the " · " dividers left out, and with a `contentDescription` on Android.
- The Android layouts follow the iOS ones' structure (a header with the count of what's left out at its end, Up Next's later classes as a row each with the time at the end, under their own label in a tall widget) in Material styling. Rows sit at the top with fixed gaps, leaving any space below empty (unlike iOS, which spreads them when some are left out). What Android can't draw (live countdowns) is left out.
- Each platform's layouts share their common parts through a kit (`widgets/kit.tsx`, `widgets/kit.android.tsx`), which is itself a `'widget'` function handed to the layouts by `withWidgetKit`. Layouts import their kit by a relative path: the build's layout registry bundle makes every bare import but `expo-widgets` an empty module.
- Our expo-widgets and @expo/ui patches add what the layouts need and upstream lacks (`patches/README.md`): on iOS `ViewThatFits`, and a live countdown without seconds (`kit.countdown`, a `Text`); on Android per-row links, spoken descriptions and more of the system's state in `environment`; on both, the system locale for the first-run text.
- The widget extension runs in the system language, so each iOS layout sets SwiftUI's `locale` to the app's language, and countdowns match the text the app writes.
- A widget lays a live date out once, when it renders, and a live date takes all the width it's offered. So a countdown goes inside the Text it's read with when nothing after it in the line needs room (it's cut with that text), and on its own takes the width of the widest value it will show, drawn in the same font as the text around it.
- First run: the build embeds each layout with empty props (the layout registry configs on both platforms), so a widget added before learnX has run, and its preview in the widget gallery, asks to open learnX instead of showing nothing. The widget runtime has no translations, so that text follows the system language from `environment.locale`. The layout the app stores at runtime wins over the embedded one. On Android, Gradle doesn't track the embedded layouts as inputs, so a layout change may need a clean build.
- We don't use prebuild, so the native setup the expo-widgets config plugin would generate is checked in (the iOS extension target and its Podfile target, Info.plist keys, Android's providers and their resources). When upgrading expo-widgets, run its config plugin in a throwaway prebuild copy and compare. Adding a widget means a Swift widget in `ios/ExpoWidgetsTarget/index.swift`, a provider on Android, an entry in `expo_widgets_names`, and its layouts in both layout registry configs. The Android widget picker's previews are static XML copies of the layouts.

# src/services

Code that talks to the system and to servers outside `data/source`: background sync, notifications and reminders, the system calendar, Spotlight and App Intents, the widgets' feed, downloaded files, crash reporting and courseX. How it's tested is under "Unit tests" in the root `AGENTS.md`.

In the Electron app only the deadline and class reminders run among the surfaces (no widgets, Spotlight, App Intents or calendar sync); its own services are `services/files/electron.ts` (Open in Default App, Save As), `services/calendar/electronExport.ts` (the .ics export) and `services/electronUpdates.ts`. See `electron/AGENTS.md`.

## Surfaces

- `services/surfaces` keeps what learnX shows outside the app in step with its data: the Deadlines and Next Up widgets, deadline and class reminders, Spotlight, the App Intents' data, the assignments written to the system calendar or Reminders, and the courses shared with courseX (Settings › Course Information Sharing). `watchSurfaces()` (from `index.js`, so it runs in every JS runtime: the app, the background task and Android's notification action task) follows the cached assignments, notices, courses and timetable, the user data it reads (the semester shown, hidden courses, archives) and the settings, and `refreshSurfaces()` updates each output whose inputs changed (compared like an effect's dependencies), one run at a time. Code the system may stop soon after (the background sync, notification actions) awaits `refreshSurfaces()`; logout calls `clearSurfaces()`.
- Don't call the widget, Spotlight, reminder, calendar or courseX functions from screens or hooks: change the data and the surfaces follow. An output's update throws or rejects when it fails (the widgets, the App Intents, the reminders): `refreshSurfaces` reports it to Crashlytics and runs it again with the next refresh, so an output doesn't swallow its own errors (Spotlight reports and recovers its own, see `modules/AGENTS.md`). A failed calendar write reaches the app through `subscribeSurfaceErrors` (shown as a toast). To add an output, add an entry to `surfaces` with its dependencies and update function. The calendar and Reminders outputs also have a `missing` check, run when nothing they depend on changed (on the first refresh, the first after the app comes back, and otherwise at most once a minute, `MISSING_CHECK_MS`), so entries (or a whole calendar or list) the user deleted in Calendar or Reminders are written again: one listing of the calendar, never a permission prompt.

## Downloads

- Downloaded files are the app's own and kept by ids, never names: `<Caches>/downloads/<course id>/<file id>/<title>.<ext>` (`services/files/downloads`), with a `course.json` beside each course's files (its names and semester) for when the course isn't cached. A download is written to `<Caches>/downloads-partial/` and moved into `downloads` only once it is whole, so a file there is always complete; what a killed download leaves behind is deleted before the next run's first download. Course names follow the app's language, so a path built from one would break after a language change. People get files out through Downloads › Export (`services/files/export`): a folder they pick with the system picker (on Mac too, with the user-selected read-write entitlement) gets `learnX/<semester>/<course>/<title>.<ext>` in the app's language. Sharing, opening and saving on Mac name a file by its title alone. The Mac app has no Downloads folder access: Download on a file and Export Synced Events ask where to save with the system save panel (`saveFile` in `modules/share`, `UIDocumentPickerViewController` for exporting a copy). The app's Documents folder isn't shown in Files or Finder (no `UIFileSharingEnabled`): it holds the app's databases, not files for people.
